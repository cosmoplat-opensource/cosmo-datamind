# 关系的多通道交叉复核与数据清洗

`ontology-semi-auto` 用取值重叠裁决关系。取值重叠只说明「子键的值在父键里出现过」:
两张表的自增 id 落在同一区间、几乎每张表都带的租户编号,都能让它达标。
本技能在两个环节补上独立证据:提议时少提这类关系,构建后逐条复核。

## 1. 提议时

- **不提 id 对 id 的关系**,除非子键名能指向父表(如 group_id → 分组表),或两边存有可对照的名称列。
- **租户键不逐表提议**:被大量表共用的编号列(企业、租户、组织编号)只在主数据上建一次归属,
  其余对象在说明中注明「按该编号隔离」。
- **多态引用写明判别条件**:同一编号列按类型列指向不同的表时,每个目标各提一条关系,
  child_key 写编号列,rationale 写「当 类型列 = 值 时」。
- **同一对表只提一个方向**:从引用方指向被引用方;不要为同一对表同时提 A→B 与 B→A。
- **有冗余名称时写出来**:子表同时存了编号和名称(如 xx_no 与 xx_name),在 rationale 中注明,
  复核时会按键关联比对两边的名称。

## 2. 构建后复核

构建台选中本技能时,在数据裁决之后、验收检查之前自动运行,步骤记为「交叉复核」「数据清洗规则」。
也可对已有产物与裁决所用的库(可以是只读抽样库)手动运行:

```
run.sh --ir <构建产物.json> --db <SQLite 库> --report <报告.json> [--clean] [--apply <新产物.json>]
```

只读、只用标准库,不改原文件。每条已验证关系检查以下通道:

| 通道 | 判定 | 冲突强度 |
|---|---|---|
| 冗余名称 | 按键关联后两边名称一致率 ≥ 90% 为支持,< 50% 为冲突 | 父键为自增 id 时强;父键为业务编码时弱(多为冗余名称过期) |
| 自增 id 碰撞 | 父键是 id、子键名与父表无关、名称通道不支持 | 强 |
| 双向 | 同一对表两个方向都被判为已验证 | 弱 |
| 软删除 | 只看父表未删除行,重叠率跌破阈值 | 弱 |
| 时间先后 | 超过 20% 的子记录创建时间早于父记录一天以上 | 弱 |
| 租户键 | 子键被 20% 以上的表共用 | 标记 |

未通过的候选关系,若子表带判别列,再按判别值分开看重叠率;某个取值下达标的,
标为「条件成立」,建议建成按类型区分的关联(每组至少 5 个不同值才算)。
重叠达标却因父键不唯一被拒的候选,再看**有效行**:排除软删除行,或同一业务键按时间取最新
(重复不超过 5%)后父键唯一的,标为「有效行成立」,送复核。

## 3. 数据清洗(`--clean`):问题由智能体处理,不靠人反馈

业务库里的编码冲突、标错、悬空引用反复出现。清洗只读源库,产出声明式规则
(问题、证据、建议动作、可套进清洗视图的 SQL 片段),挂到对应对象的 `evidence.cleaning`:

- **码表判定**:从字典类表与字段注释收集码表;取值覆盖 ≥ 90%、且码表名与字段名相符(或就是字段自己的注释)才采用。
  注释覆盖不了实际取值时以数据为准,注释记为有误;同名字段用了不同码表时按标签给出对照,不合并。
- **离群编码**:实体类别应当决定业务编码(如计量器具类别 → 能源类型)。类别可来自本表,
  也可沿关系取父表;一致率 ≥ 90% 时,少数不一致的行给出按多数值更正的建议。
- **悬空但语义成立**:重叠率不达标、但父表类别仍强烈决定子表编码的关联,说明连对了表,
  低重叠来自悬空引用;不丢弃,改为待复核,并单独报告悬空比例。
- **悬空引用**:给出比例与排除条件;比例高时不用于完整性汇总。
- **迁移空壳**:同名表一份为空、一份有数据,绑定有数据的那份。
- **注释编码不符**:数据里有注释没写的编码,由其他码表解释的以实际码表为准,否则按「未知」处理。

## 4. 如何使用结论

- **强冲突**(refuted):`--apply` 时降为候选,原裁决写进 `evidence.cross_check.prev_status`,送人工复核。
- **弱冲突**(review):不改裁决,进入人工复核队列。它们常有业务原因:分组是后来补建的、
  引用了已删除的父行、一对一扩展表。
- **有独立支持**(corroborated)与 **仅单通道**(single_channel)分开报告;后者不是错,
  只是除重叠率外没有别的证据,抽检时优先看。
- **租户键**:从业务关系中收敛,改为对象说明。
- **条件成立**:按判别条件重新提议,不直接升为已验证。
- 问数时自动套用:离群编码经只读连接上的同名临时视图更正,码表、悬空与空壳提示交给模型;
  请求带 `clean: false` 可按原始数据作答。更正前看离群行是否另有业务原因。源库一律不改。
- 不以任何单一通道定案;多个通道冲突时,在复核队列中写明是哪几个通道。
