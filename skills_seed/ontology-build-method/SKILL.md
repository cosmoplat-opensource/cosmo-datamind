# 本体半自动构建的统一方法

`ontology-semi-auto` 规定证据契约,`ontology-cross-check` 负责复核与清洗,领域技能给出概念骨架。
本技能规定所有场景共用的做法:**表不等于概念**,先弄清两者怎么对应,再建。

本技能中的几个术语:

- **表族**:同一业务实体按层级、厂区、来源约定、站点或副本复制出的一组表。
- **类别拆分**:一张实例表按类别编码存放多种概念时,按类别拆成多个子概念。
- **有效行**:判断父键唯一与取值重叠时应计入的行,排除已删除行、旧版本、测试数据等。
- **代码契约**:从上传的后端 SQL 与前端代码中读出的表间连接条件、码表分组与字段含义。

## 1. 三层

- **概念层**:领域概念与业务关系,来自行业参照、类别目录、字典、界面与接口契约、标准。
- **映射层**:概念 ↔ 表 / 表族 / 按类别的行子集 / 字典值 / 指标编码。
- **数据层**:映射是否成立的多通道证据。

## 2. 场景画像:同一套方法,两种常见形态(可并存)

| 形态 | 识别信号 | 表与概念 |
|---|---|---|
| 多厂多层湖仓 | 表名带层级、厂区、来源、站点前缀;大量同名表 | **多表一概念**:同一业务词根的表族建一个对象 |
| 元数据驱动业务库 | 类型 / 类别目录表、实例表带类别编码、指标与量测是目录里的行 | **一表多概念**:实例表按类别码拆成子概念,目录行提升为概念 |

构建体检会给出表族、类别拆分与版本重复线索;按线索建模,不要一张表建一个对象。

## 3. 构建流程(每一步对应平台环节)

1. **体检**:无外键、软删除、版本重复、多态引用、审计与信封列、表族、类别拆分、演示与分表。
2. **画像与参照**:按形态定策略;行业参照与领域技能按体检建议选用,不同领域分开建(如能源与碳排放)。
3. **概念层**:先列概念骨架,再开始映射。
4. **分轮映射**:主数据与类型层先建;表族只建代表表,其余成员挂到同一个对象上。
5. **裁决**:数据验证只判「连接成立」,不判业务语义。
6. **交叉复核与清洗**:多通道复核关系,编码冲突、标错、悬空引用由清洗规则处理,源库不改。
7. **验收**:用界面、接口、看板上的真实问题检验本体能否回答。

## 4. 对应规则

- 表族:层级、厂区、站点、备份与离线副本、两种命名约定(如 t_ / tb_)下的同一实体,合为一个概念;
  各层列名可能不同(明细层常加前缀),映射按成员表的实际列。同族成员之间不建业务关系。
- 类别拆分:按类别编码与目录名称建子概念,evidence 写明类别码与筛选条件。
- 关联表建成关系;带业务属性的关联(系数、运算符、生效期)才建成关联对象。
- 配置、模板、日志、报表表作为信息记录,挂到它描述的业务概念上。
- 信封列(租户、组织、公司编码、审计、分区)几乎每张表都有:共享它们不构成业务关系,只在主数据上建一次归属。
  租户列常是键的作用域:编号按租户(企业、工厂)复用时,「租户 + 编号」才是键。

## 5. 有效行:先定哪些行算数,再判唯一与重叠

父键「不唯一」多半不是关系错了,而是下面四种情况之一,先按有效行复核,不要直接放弃关系:
软删除(已删除行还在表里)、版本重复(同一业务键多次入仓,同键名称一致,按时间取最新)、
租户作用域(编号按租户复用)、分组编码(字典编码按分组复用,分组条件见代码契约)。
测试与演示数据、迁移空壳同样不算有效行。

## 6. 证据与对齐

- 证据强弱:代码契约(后端 SQL 的 JOIN、前端调用链)> 声明约束 > 多通道数据证据 > 文档与注释 > 命名。
- 代码与文档照原样上传(代码包 zip、Word 文档都会读取,内网地址自动去除):连接契约在裁决中
  替代命名证据(数据门槛不变),码表契约给出字典分组;按契约提议时写出 child_key / parent_key。
- 类型对齐:贴源层(ODS)常全为字符串,物化到本地要保持同一类型,否则重叠率会假性为 0。
- 时点对齐:分区表按同一时段取样,父端取全量键集;文档数字注明采集时点。
