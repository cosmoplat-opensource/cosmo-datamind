# 本体半自动构建

按以下顺序工作。让模型提出候选项，但不要让模型自行决定 `verified`；模型的语义判断也不得覆盖可重复的数据验证结果。

## 1. 确定范围与验收问题

- 将用户目标整理为对象范围、事件范围、数据源和验收问题
  （即本体建成后应当能回答的业务问题；学界称「能力问题 / Competency Questions」，
  对外一律用「验收问题」，行话业务方看不懂）。
- 验收问题既是构建输入，也是构建后的验收用例；没有时明确标注“未提供”，不要伪造覆盖率。

## 2. 建立来源清单

- 记录真实表、列、声明主外键、代码位置、可解析文档片段和业务术语来源。
- 对象优先绑定真实表；文档推断对象必须标为候选并记录来源。
- 无法解析的附件只能记为待处理来源，不得当作已经读取的证据。
- 将历史人工否决模式作为负例，减少重复误判。

## 3. 生成候选项

- 提议对象、事件、关系以及属加种差定义；没有足够依据时将定义留空。
- 每条关系给出 `source`、`target`、`verb`、`rationale`；若能从 schema 判断连接键，再给出 `child_key`、`parent_key` 作为候选提示。
- 候选键只是搜索优先级，不是证据；必须验证列真实存在。

## 4. 用统一规则验证关系

- 计算 `|child distinct ∩ parent distinct| / |child distinct|`。
- `verified` 至少要求：重叠率达到固定阈值、父键唯一、键名或父表名有语义证据、方向不是唯一子列指向非唯一父列。
- 声明外键可作为直接证据；复合键按元组联合计算，不得拆成两个单列关系冒充。
- 将 `verified` 严格解释为“数据库连接关系已通过验证”，不要把它解释为业务语义已经正确。
- 语义复核存疑时加入人工复核队列，不自动推翻数据验证结果；无可复核依据的关系保留为 `candidate`，不要静默删除。
- 不在未评测的数据集上启用自适应阈值。小维表、共享值域和自增代理键是重点假阳性族。

## 5. 检查 BFO/IOF 映射

- 将上层类别称为“BFO/IOF 上层类别”，不要把 `InformationContentEntity`、`MaterialArtifact` 等 IOF Core 类称为 BFO 顶级类。
- 只使用官方发布物中的类和关系 IRI，并检查关系的定义域和值域。不得拼接或猜测外部 IRI。
- 提议关系时，若该业务动词确实对应一个官方关系，就在 `founded_relation` 里给出关系名
  （可选值由构建器在提示词中列出，取自实现里的官方关系表，不要凭记忆另写）；
  同时自查定义域与值域：`hasInput`/`hasOutput` 的源必须是事件或动作类对象，
  `describes` 的源必须是信息内容实体，`bearerOf` 的目标必须是角色、性质或倾向。
- 拿不准就把 `founded_relation` 留空。留空只是「未接地」，后续可由人工补；
  填错则是伪造一条看似符合标准、实则不成立的映射，后者严重得多。
- 业务动词本身照常填在 `verb` 里：接地与否不改变业务表达，只决定这条关系能否
  声称对齐了上层本体。
- 将数据库外键、字段重叠和通用动词“关联”保留为本地对象属性；这些信息不足以确定 BFO/IOF 关系。
- 对“归属”“服务”“触发”等依赖上下文的动词不做自动映射。无法确认时写入 `grounding_status=unmapped` 和原因。
- 分开记录连接验证状态与上层关系映射状态：`status` 表示数据验证结果，`grounding_status` 表示 BFO/IOF 映射结果。

## 6. 执行确定性验收检查

- 检查悬空端点、自反误判、状态冲突、重复/双向边和孤岛。
- 审计每条 `verified` 的连接键、重叠率、父键唯一性、命名证据和方向记录。
- 评分定义的非循环性、属加种差和反例；低质量定义进入待改进队列。
- 有验收问题时执行结构可达性核验；`partial` 和 `unanswerable` 形成下一轮缺口。
- 上层关系映射另行检查官方 IRI、关系方向以及源、目标类别相容性。
- 悬空端点、状态冲突或不满足证据契约的 `verified` 产生 `fail`；候选关系、语义争议、孤岛、定义不足和映射存疑产生 `review`。

## 7. 保存记录并提交人工复核

- 保存提议依据、数据验证信号、决定原因、语义复核、上层关系映射和验收检查报告。
- 人工确认产生 `asserted`，不要改写为 `verified`；将人工否决样本加入后续任务的负例。
- 若有窄/宽时间窗数据，复算关系并记录状态迁移；没有宽窗证据时明确写“未复检”，不要声称稳定。

## 输出要求

- 每个对象至少包含标识、显示名、类型、来源、定义状态和开发状态。
- 每条关系至少包含源、目标、动词、`status`、结构化验证依据、`grounding_status`；成功映射时再包含 `founded_relation`、官方 IRI 和时间限定。
- 报告同时列出阻断问题、待复核项、验收问题结果和未处理来源。没有数据时返回明确的失败原因，不生成空壳本体。
