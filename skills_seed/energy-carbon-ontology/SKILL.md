# 能源与碳排放本体半自动构建

与 `ontology-semi-auto`、`ontology-cross-check` 同时启用。前者规定证据契约(谁能判 verified、如何记录依据),
后者补上取值重叠之外的独立证据;本技能规定这个领域「建什么、怎么切分、哪些陷阱要先识别」。

## 0. 构建流程:每一步做什么

1. **体检**(构建体检):先看无外键、软删除、多态引用、审计列、枢纽键、演示与分表,对照第 4 节的陷阱。
2. **分流**:能源用「能源管理」参照,碳排放用「碳排放核算」参照,分两个本体或两组轮次。
3. **概念层**:按第 2、3 节的骨架,从类别目录、字典、指标目录与界面标签定概念,再开始映射。
4. **映射**(分轮构建):类型与组织层先建;表、按类别码的行子集、字典值、指标编码映射到概念。
5. **裁决**:数据验证只判「连接成立」,不判业务语义。
6. **交叉复核与清洗**:用 `ontology-cross-check` 复核产物并生成清洗规则;强冲突降为候选,
   弱冲突与租户键进入人工复核;编码冲突与悬空引用由清洗规则处理。
7. **桥接与验收**:按第 3 节接到碳排放侧;用界面视图写成的验收问题检验本体能否回答。

## 1. 先定概念层,再做映射——不要一张表建一个对象

能源管理系统通常是元数据驱动的:业务概念大多不在表名里,而在「实例表的行 + 类别目录」里。
一张表建一个对象,产出的是数据库结构的镜像,不是领域本体。

- 对象对应**领域概念**,不对应表。一个概念可以由多张表共同承载(主表、明细、配置);
  一张实例表也可能按类别码拆成多个概念。
- 按类别目录定概念:设备表里按设备类别码区分的「电能表 / 流量计 / 蒸汽表 / 逆变器 / 储能变流器」,
  是「能源计量器具」「发电设备」「储能设备」等概念的**实例子集**;系统表里的「用能系统 / 子用能系统 /
  园区 / 光伏站 / 储能站」构成「用能单元」的层级。在 evidence 里写明类别码与筛选条件。
- **关联表建成关系,不建成对象**(表名以 _rel、_relation、_mapping 结尾,且主要由两个编号列构成)。
  只有当关联本身带业务属性(系数、运算符、生效期)时,才建成「关联对象」。计量关系即属此类:
  它规定「某用能单元的用量 = 若干计量对象按运算符与系数计算」,应建成带属性的关联对象。
- 配置表、模板表、日志表、报表表默认建成信息记录(ice),并挂到它所描述的业务概念上;
  不为每张配置表单独提议业务关系。

## 2. 能源侧概念骨架(按需取用,没有证据就不建)

组织与范围:企业、用能单元(含层级)、用能单元组。
计量:能源计量器具、测点(量测实例)、量测定义、计量关系。
能源:能源介质(电、水、蒸汽、天然气、压缩空气、光伏、储能等——以**字典值**为个体,不为每种介质建表)、
能源消耗量、折标煤量、能源价格、能耗账单。
指标:指标定义、指标实例、指标公式、指标参数、周期。**指标目录的行本身就是领域概念**
(如用电量、用电费、电单耗),对关键指标要按编码提升为概念并保留公式依赖。
管理:能源计划与目标、能源基准、能源绩效参数、用能诊断。
运维过程(event):告警、工单、巡检、缺陷——按「告警 → 工单 → 处理」的顺序建事件链。
发电与储能:光伏站、储能站、逆变器、储能变流器。

## 3. 碳排放侧:依据标准建,不要从库表硬凑

多数能源管理系统没有碳核算实体表,碳排放只以派生指标存在(如「用电碳排 = 用电量 × 系数」)。
此时碳排放本体依据 GB/T 32150-2025、ISO 14064-1 / GHG Protocol 建:

- 核算边界(组织边界、运营边界)、排放源、排放范围(范围一 / 二 / 三)、活动数据、排放因子、
  温室气体排放量、排放强度、减排量、核算过程记录。
- **排放因子必须作为独立概念**:数值、单位、适用能源介质、来源标准、地区、年份、有效期。
  库里若只把因子写成公式常数,在 evidence 中如实记录,并把「因子不可追溯」列为待复核问题,
  不要替它编造来源。
- 桥接:活动数据引用能源侧的「能源消耗量」(指标实例);排放源 = 用能单元 × 能源介质;
  排放范围由能源介质与来源(外购 / 自产)决定。
- 二次能源(厂内制取的压缩空气、自产蒸汽)不单独计排放;总排放按范围分别汇总后再合计。
- 能源侧与碳排放侧分两个本体或两个独立轮次构建,各自使用对应的行业参照
  (能源管理 / 碳排放核算),不要把碳侧概念当作能源参照的可选附属。

## 4. 先识别再裁决:这个领域的常见陷阱

- **租户键不是业务关系**:几乎每张表都带企业编号。「X 归属企业」只在少数主数据表上建一次,
  其余在对象说明中注明「按企业隔离」,不要为每张表提议一条归属关系。
- **多态引用**:同一个对象编号按类型列(0 设备 / 1 系统)指向不同的表,应建成按类型区分的关联,
  child_key 写编号列,并在 rationale 写明判别条件。
- **类别作用域编码**:量测编码、指标编码在不同类别下复用,真正的键是「类别编码 + 编码」(及模板)。
- **软删除**:类型表常有大量已删除行,唯一性与重叠要在未删除行上看;给出键时在 rationale 注明删除标记列。
- **编码口径冲突**:同名的能源类型字段在不同表里可能使用不同的字典(甚至注释本身写错)。
  把能源类型字段关联到它实际使用的那套字典,不同字典之间只建映射,不合并。
- **自增 id 碰撞**:两张表都用 id 关联、又没有名称或业务证据时,不要提议关系。
- **迁移空壳**:同名表若在多个库中存在,绑定有数据的那一份。

## 5. 交叉验证与验收

- 用前端或接口代码中的真实调用链(用能单元树 → 分项能源 → 用量 / 费用 → 计量点位 → 计量关系)
  写验收问题,例如「某用能单元某日的累计用电与电费是多少」「某用能单元由哪些计量点按什么公式计算」。
- 除取值重叠外,优先寻找独立证据:冗余名称是否一致、时间先后是否合理、按类型分条件的重叠
  (`ontology-cross-check` 可对产物逐条复核)。多个证据冲突时进入人工复核,不以任何单一证据定案。
- 能源类型等编码字段,用实际取值集合反推它用的是哪套字典;码表对照、标错更正与悬空引用
  交给 `ontology-cross-check` 的清洗规则处理(挂在对象上,取数时套用),源库不改。
- 能源侧、碳排放侧分别报告覆盖与缺口;碳侧缺少核算实体时如实写「依据标准补建」,不生成空壳对象。
