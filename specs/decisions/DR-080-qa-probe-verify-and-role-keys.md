## 上下文 / Context

BIRD Mini-Dev 对比实验中,DataMind 问数(精确作答)在测试集上只有 23.5%。
同一骨干模型的 ReAct 智能体为 42.6%,换用 DataMind 本体后为 43.4%,说明问题不在本体。
在验证集上逐题诊断,原因如下:

1. **一次生成,不看数据。** 问数只依据召回的上下文生成一次 SQL,不能先查看取值、试运行;出错或结果为空也不再修正。
2. **精确作答规则没有生效。** 规划和修正在守护线程(`_bounded`)中运行,普通线程不继承 contextvars,
   作答形式(`_ANSWER_STYLE`)与问数执行库(`_QA_DB`)在线程里都丢失了。
   DR-079 的测试集结果因此是按报告式规则得到的;另外,探查查到的是主库而非本体来源库。
3. **召回不全时编造表名。** 上下文只列召回的表,缺表时模型自造表名,被本体约束校验拦下后拒答。
4. **字符串常量里的词被当成表名。** `WHERE Title = '... from experts'` 被解析出表 `experts`,校验与意图核对都受影响。
5. **意图核对过严。** SQL 通过持有外键的子表回答问题(考勤表的活动外键之于"活动")时,被判为答非所问而拒答。
6. **同一对表只保留一个键。** `superhero` 的 `eye/hair/skin_colour_id` 都指向 `colour.id`,裁决只留一个,
   另两个 JOIN 被拦下。业务库中同类情况常见:制单人与审核人都指向员工,出库仓与入库仓都指向仓库。
7. **日期格式与取值位置要靠猜。** 上下文不给日期列的格式;问句里的编号、名称、金额不知道对应哪一列。

## 决定 / Decision

1. **先探查。** 规划时模型可先输出只读探查查询(`{"probes": [...]}`),看到结果后再给出分析。
   - 每轮最多 3 条,每条最多返回 20 行,最多 2 轮;最后一轮要求必须给出分析;
   - 执行器只读、使用问数执行库,出错时把错误原文返回给模型。
2. **按结果核对。** 执行后把结果列、行数和前 5 行交给模型核对一次:是否直接回答了问题、是否多带了列、空结果时条件是否用错。
   - 需要改写时,改写后的 SQL 照样过本体约束校验;
   - 精确作答每次核对,报告式只在出错或结果为空时核对。
3. **守护线程带上请求上下文。** `_bounded`、`_bounded_stream` 以及流式问数的规划、叙述线程都用 `contextvars.copy_context()` 运行。
4. **列出其余表名。** 上下文末尾列出本体中未展开的全部表名(最多 400 张)。
5. **解析表名前先去掉字符串常量。** 只用于本体约束校验与意图核对的表名解析;有效行等条件校验仍看原文。
6. **意图核对认可外键子表。** SQL 所用的表持有指向问句对象的已验证外键时,判为 partial,不拒答。反方向(只查了问句对象的上级表)仍判答非所问。
7. **角色键。** 关系裁决成立后,子表中其他键名指向该父表、且通过同样数据判据的列,记入 `evidence.role_keys`。
   - 每对表仍只保留一条关系;
   - 本体约束校验与 JOIN 提示都认可这些角色键。
8. **日期示例与取值出处。**
   - 日期、时间列给出一个实际取值作为格式示例;
   - 问句中的编号、引号内文本、带小数的数,在库中等值查到后写成"问句中的取值出处:X → 表.列";
   - 精确作答规则增加"按列取最大、最小时先排除该列为 NULL 的行"。
9. 流式问数同样启用探查。

## 后果 / Consequences

**BIRD Mini-Dev(DeepSeek-V4-Flash,冻结划分):**

| 集合 | 修改前 | 修改后 | 对照 |
|---|---|---|---|
| 验证集(75 题,用于诊断与调整) | 22 | 35 | ReAct 基线 35 |
| 测试集(251 题,只运行一次) | 59(23.5%) | 106(42.2%) | ReAct 基线 107(42.6%);ReAct + DataMind 本体 109(43.4%) |

- 每题平均耗时约 2.5 秒(验证集)。
- 108/200 表合成库回归:关系指标不变。问数 108 表 8/12(此前 9/12)、200 表 15/16。
  108 表少答对的一题是"接单金额合计(不含税)":模型改用了发票的不含税金额,问句本身有两种理解,此前评估中同题也有过波动。
