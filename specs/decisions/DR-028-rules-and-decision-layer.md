# DR-028 · 业务规则约束与决策层

- **状态 / Status**: accepted
- **日期 / Date**: 2026-08-02
- **关联 / Refs**: [[DR-015-palantir-actions]](行动层)、[[DR-027-business-aliases-and-change-audit]]、[[DR-013-human-review-relations]]

## 背景 / Context

第三遍对照《本体智能研究报告(1.0)》,这次不按六阶段而按**三层架构**逐层核对,
发现了此前三轮都没看出的**结构性空白**:

| 报告三层 | 要素 | 我们 |
|---|---|---|
| 语义层 | 对象 / 属性 / 关系 / **规则与约束** | 前三个 ✓,**第四个缺** |
| **决策层** | 逻辑推理 / 一致性校验 / 触发条件 / 业务判定 | **整层缺失** |
| 行动层 | API / 工作流 / 动作编排 / 权限控制 | ✓(动作中心) |

报告对决策层的要求很具体:

> 逻辑推理基于语义层的概念关系与业务规则,推导出未显式记录的**隐含结论**,
> 如由审批层级与金额规则推导出某笔订单应走的审批路径。
> ……形成完整可追溯的**决策路径**——每一条结论均可回溯至具体规则依据,支持合规审计与业务解释。

我们的动作层有风险分级,但**触发条件靠人判断**;报告要的是从规则自动推导。
现有 `/api/ont/rules` 名字像但不是——它返回的是构成规则统计与方法论说明,
不是业务规则。

## 决定 / Decision

新增 `rule_engine.py` 与四个端点,补齐语义层第四要素与整个决策层:

- `GET/POST /api/ont/rulebook/<key>` + `/delete` —— 业务规则 CRUD
- `POST /api/ont/decide/<key>` —— 规则求值,推导隐含结论

规则形态刻意保持朴素(不引入规则 DSL):
`{id, cn, on(作用对象), when[{field,op,value}], then{decision,action,severity}, note}`

## 为什么这样做 / Rationale

- **推理必须确定性,不调 LLM**。规则是业务写死的逻辑边界,用模型推会把概率当逻辑;
  且报告要求"每条结论可回溯至具体规则依据",模型给不了这种回溯。
- **每条结论必带 trace**。返回"依据哪条规则、哪个字段、什么阈值、实际值多少"——
  这是合规审计的最低要求,也是与"猜一个"的分界线。
- **冲突必须报出来,不能静默取一条**。两条规则对同一动作给出不同结论时,
  系统**无权替业务择一**;静默取第一条等于把冲突藏进黑箱,且求值结果会取决于
  规则顺序(不可预期)。
- **规则须锚定到本体已有对象**。规则的 `on` 不在本体中一律拒收——
  游离于本体之外的规则无法参与语义层协同,那只是又一处散落的硬编码。
- **数值比较按数值**。字段传字符串 `"250000"` 时若按字符串比,`"250000" < "99"` 成立,
  会产生完全错误的判定。已做数值优先转换。

## 影响 / Consequences

- 语义层四要素补齐;决策层从无到有。
- 规则集提供**静态一致性校验**(不看数据):查重复 id、查"条件相同结论不同"的矛盾。
- 规则可挂到动作(`then.action`),为后续"规则触发动作"打通接口。

## 代价与边界 / Trade-offs

- 条件间为 **AND 语义**,不支持 OR/嵌套。刻意为之:朴素规则可被业务直接读懂,
  引入布尔表达式树会让规则变成只有工程师能维护的代码。需要 OR 时拆成多条规则,
  可读性反而更好。
- **未触发 ≠ 合规**。只说明现有规则未覆盖该情形,不代表这笔业务没问题。
  已在返回的 `note` 中标注,防止被误读为"检查通过"。
- 一致性校验是**静态**的:通过不代表规则业务上正确,只代表规则集内部不自相矛盾。

## 实测发现的一个真问题(已修)

多场景测深度问数时发现:给对象加了业务别名后,`/api/ont/cq` 立刻认,
但**问数链路仍答不上**。查下来不是别名失效,而是**问数结果缓存不随本体变更失效**——
`_qa_key` 已含上传库指纹,却漏了本体编辑指纹。

本体是问数的语义锚点(召回、口径、双盲全靠它),改了本体却复用旧答案,
用户会持续拿到旧语义下的结果。已把编辑日志 mtime 并入缓存键。
断言 RL19 锁定该行为。
