# DR-051 · 内置技能可改写与可删除(覆盖层 + 删除墓碑)

- **状态 / Status**: accepted
- **日期 / Date**: 2026-08-30
- **决策者 / Deciders**: Boss(用户)+ Writer(Claude)
- **关联 / Refs**: [[DR-021-skill-management]](放开其"内置只读"约束)、[[DR-050-executable-ontology-build-gate]];
  实证=`server.py` 技能四端点 + `skill_registry.method_text`、`test_all.py` X 段、`workdir/skill_deleted.json`

## 上下文 / Context

DR-021 把内置技能定为只读:改只能"复制为自定义副本",删则一律 400。理由是内置技能
是建模规则的种子,不该被破坏。

实际使用下来这条约束挡住的是正当需求:用户要调的往往正是内置技能的正文(它才是真正
注入构建提示词的那一份),被迫复制成副本后,构建时要记得改选副本,列表里还多出一条
近乎同名的技能。而"不给改"并没有换来安全——出厂正文本来就在版本库里,随时可复原。

同时发现一处既有不一致:`skill_registry.method_text` 里**内置优先于自定义**,而查看接口
是自定义优先。若按 DR-021 允许同名副本,查看页显示已改、构建却仍用出厂正文——
**改一处不生效,比不给改更容易误导人**。

## 决定 / Decision

内置技能一律可编辑、可删除,但不动出厂文件,改用两层间接:

### 1. 改写 = workdir 覆盖层

保存内置技能名时,内容写入 `workdir/custom_skills/<name>.md`,`skills_seed/` 与上游引擎
目录原样不动。查看、列表描述、构建注入一律**以覆盖件优先**(`method_text` 的解析顺序
已同步改为自定义优先),列表上标「已改写」。

不直接改 `skills_seed/` 的两个理由:一是会弄脏版本库,`git checkout` 后改动消失,用户
以为改过其实没有;二是上游引擎的技能目录不归本服务管辖,根本无权改写。

### 2. 删除 = 墓碑,不是删文件

删除内置技能时记入 `workdir/skill_deleted.json`:列表不再展示,`_skill_method_text`
不再注入(**界面上看不见却还在影响构建,是最难查的一类不一致**)。出厂正文保留,
可一键恢复。自定义技能没有出厂版本,仍是真删文件。

### 3. 恢复默认必须点得到

删除后技能从列表消失,若无入口,"可恢复"就是空话。故列表接口把已隐藏的内置技能
带 `hidden` 标记一并回传,界面收在末尾一行「已隐藏 N 个内置技能:xxx 恢复」;
改写过的则在编辑弹窗里显示「恢复默认」。新增 `POST /api/build/skill/restore`
同时撤销改写与删除;对自定义技能返回 400(没有出厂版本可恢复)。

## 影响 / Consequences

- (+) 用户能直接调真正生效的那份技能正文,不必绕副本。
- (+) 顺带修掉「改写不进构建」的解析顺序不一致。
- (+) 任何改动都可逆:出厂正文始终在,`workdir` 层可整体清掉回到初始状态。
- (−) 多了一层间接:排查"技能为何是这个内容"时要先看 `workdir/custom_skills/` 有无同名
  覆盖件、`skill_deleted.json` 有无墓碑。列表的「已改写」标记与编辑页文案即为提示。
- **边界**:墓碑与覆盖件属本机偏好,已 gitignore,不随仓分发;克隆者拿到的始终是出厂技能。
