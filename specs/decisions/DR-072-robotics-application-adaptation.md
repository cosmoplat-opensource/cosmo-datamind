# DR-072 · 机器人应用检查与可追溯补全

- **状态 / Status**：accepted（IR-026 已于 2026-11-13 经 T06 技术验收和用户提交指令确认交付）。
- **日期 / Date**：2026-11-12。
- **更新 / Updated**：2026-11-13。
- **关联 / Refs**：[IR-026](../iterations/IR-026-robotics-application-adaptation.md)、[总方案](../../docs/datamind-application-contract-design.md)。

## 上下文 / Context

通用新本体可以保存大量实例，但仍可能缺少当前 UR 消费者需要的执行字段与业务配置。类别齐全也不能替代提取和消费者适配。

## 决定 / Decision

以下为已确认决定；2026-11-13 的自动匹配补充替代原先默认人工确认角色、再单独提交生成的交互。

1. 现有 TBox＋ABox 构建完成直接入库；仅当用户在该本体页点击“基于此本体生成行为树”时，由后端自动匹配契约并检查 TBox 必需角色、关系方向、属性范围及执行语义；构建时不预置这些要求。第一版仍限定当前固定 UR 抓移放和已支持 XML 范围。

2. 复用 Yang 确定性核心识别 XML 调用、顺序、参数和数据引用；补充 treeId、xmlTag、树顺序、作用域、固定配置、内建 SetBlackboard 契约和公开配置标记。不得仅加 artifactContract 标记或退回旧构建器伪造成功。

3. 应用角色映射发生在通用 TBox＋ABox 构建完成之后，由适配层把本体术语对应到行为树消费者角色。
用户显式发起执行结构适配后，符合受控词表、规范 ID、实体种类及语义校验的对应自动通过，由后端直接受理应用版本生成。
无法确定的对应由用户选择实际本体术语，一次“确认并生成应用版本”完成校验与受理；名称相似不代表语义相同。
确实缺 TBox 时打开基于父版本的修订，重新确认后提取；检查器本身不改写本体或创建适配运行。

4. 补充可证实的感知配置、拍照关节配置、放置配置和目标位姿。若源值来自变量，只在唯一可追溯的静态赋值时解析；歧义、动态值和缺来源保持缺项。设备身份和零件／工位／槽位不凭接口名或示例模板制造。

5. 适配生成有 parent_version_id、来源摘要和规则版本的应用派生版本。保留原设计及扩展知识；执行图中的标准标识与原实例建立显式映射，避免重复可编辑配置源。来源缺失或冲突时阻止对应适配。

6. 执行结构通过后允许进入任务准备，复用 task_dialogue、task_completion、task_knowledge、grounding。对象、类型、配置关联可以逐次补全；每次保存新版本并重新检查。缺执行结构不能用业务表单补造。

7. 复用 semantics、compiler、validator、generation 和消费者。离线候选按原 offline 规则检查；严格生成按原 strict 证据要求检查，执行环境验证保持单独状态。生成不读取源 XML 兜底，已发布应用版本自包含。

8. 新版本同时保存 OWL 和一个完整 design.json，包含实际版本内容、设计血缘、适配、补全来源、覆盖和评估；引入明确的新工件版本，旧 design v1 只读字节保持不变。

## 后果 / Consequences

依赖 IR-025；执行事实适配、业务补全和工件升级分别形成可评审任务。
需要版本化检查和修复记录，增加维护成本；换取构建自由、应用诊断和执行一致性。
规范映射无需重复人工确认；自定义术语或未知词表仍需要人工核对，避免把名称相似当作业务语义一致。
自动匹配和确定性适配不调用 LLM，自动生成应用版本也不代表任务业务信息齐全或现场执行已验证。
不改变 IR-024 已交付范围，按新迭代实现并回归。

T01 详细角色、执行字段、来源、修复和工件约定见 [机器人应用适配 v1](../contracts/robotics-application-adaptation-v1.md)。
该规约在 2026-11-12 准备时待评审，随后经用户确认冻结；自动匹配后的接口和交互以 2026-11-13 补充约定为准。

2026-11-12：用户确认复用原任务业务映射步骤并要求继续，T01 已冻结进入 T02；第 11 节可执行调用面随本轮测试评审。

### 2026-11-13：可定位的骨架缺项与建模建议

用户要求应用检查明确列出缺少的类别、关系或数据属性，并在“修订本体骨架”后将此前缺项提示带入建模输入框。
报告保留稳定错误码、原实体及证据引用，补充规范角色标识、中文名称、实体种类及可用的父类、定义域、值域和数据类型要求。
缺少角色对应与缺少实际术语不混为一谈；提示先核对已有对应，存在冲突时明确要求核对语义。
修订导航携带已保存的报告或适配记录标识，目标设计必须匹配；读取与刷新不修改设计、不调用模型。
建模页展示此前缺项，按当前类别／关系属性阶段生成可编辑建议；输入框中按 Tab 或点击填入按钮只补全文本。
保留自定义输入及 Shift+Tab 的焦点行为；用户点击“确认并发送建模要求”后才提交模型请求。
已完成的本体仍由用户明确返回类别修改，按原阶段确认后继续；旧报告仅作为带历史标记的修改参考，不能充当生成许可。
已有工件和报告不就地改写，旧报告可利用已有实体引用显示缺项标识；后续复检产生新的诊断。

同日用户进一步明确：修订按钮按缺项类型直接定位阶段；只有关系或数据属性问题时保留类别确认并打开属性修订，存在类别缺项时先打开类别修订。
阶段判定覆盖同一目标的全部骨架问题，混合缺项先类别；旧报告可依据固定词表和实体引用判定 cppType 等属性。
点击修订是用户明确打开草稿的动作，可创建对应阶段的新设计修订，但不调用模型、不确认设计、不改写旧资产版本。
报告修复导航返回阶段计划；前端仅在该点击操作中显式提交带修订号和幂等标识的阶段编辑请求，普通读取、刷新和历史链接不触发阶段写入。
当前类别未确认时仍须先确认类别，不能通过属性快捷入口恢复或伪造确认。

同日用户指定简化建模提示：移除建模页的大块缺项卡片、预览和填入按钮，将当前阶段的简短修订提示词直接放在输入框的浅色占位文字中。
应用检查页继续显示具体诊断，建模输入框仍支持 Tab 填入和编辑后确认发送，普通输入、阶段选择和来源校验保持原行为。

同日用户要求模型运行可见、修订完成后优先确认：运行状态展示等待动画，区分排队、模型生成及确定性实例构建。
本轮设计成功后将确认操作置于顶部并随结果滚动保持可达，修改输入默认收起；已处理的浅色建议不在等待确认状态重复显示或被 Tab 填入。
用户可展开“继续提修改意见”再发起一轮；未发送草稿保留，失败时继续显示可编辑输入和错误，确认操作仍绑定当前修订及快照。

### 2026-11-13：自动角色匹配与应用生成

用户确认：规范映射通过时不再要求人工点击“确认并生成应用版本”，由后端直接生成；无法确定的对应才交给用户填写。
自动策略限于当前已知受控词表快照、实体种类相同及规范 ID 一致的唯一对应，仍须通过现有角色覆盖、层次、方向、范围、类型及来源校验。
不基于中文名称、相似度或模型猜测创建异名映射；异名概念作为可选择的实际完整 IRI，不作为已确定角色预选。
用户显式点击“补齐执行结构”或提交公开应用准备请求时，后端在同一事务中保存自动匹配依据并入持久队列；普通应用检查及 GET 不生成版本。
自动路径的 UI 仅展示等待进度和结果，不要求用户点击“确认并生成应用版本”。
无法确定时，保留已知对应并显示待核对项；用户一次提交完成整份映射校验与生成受理，不再要求两个独立按钮。
客户端不能提交 confirmed、automatic、ready 等授权声明；后端记录自动或人工方式、规则版本及固定 TBox 摘要，完整 JSON 保留该追溯。
相同请求并发／重放仅受理一个运行；读取、刷新和重启不重复生成，提取失败保留失败事实并等待显式重试。
缺少映射时允许先核对已有概念，确实缺少类别或属性时仍回原骨架修订；不制造业务对象，不绕过执行结构或生成前校验。
原分步确认接口保留兼容；历史待确认记录不会因打开或刷新页面自动入队，须由用户显式发起后续操作。
自动生成仍受固定父版本、工作头和修订冲突检查约束；完成后保留原版本，返回原任务及切换所用版本仍须明确操作。
