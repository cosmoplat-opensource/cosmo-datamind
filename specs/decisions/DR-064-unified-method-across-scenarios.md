## 上下文 / Context

平台先后在两类数据上做了半自动构建,各自摸索出一套做法:

| | 电子制造数据中台 | 能碳平台 |
|---|---|---|
| 形态 | 多厂多层湖仓,2,206 张表 | 元数据驱动业务库,5 库 594 张表 |
| 表与概念 | 同一实体按层级、厂区、来源约定、站点、副本复制成几十张表 | 一张实例表按类别码装着多种概念;指标、量测是目录里的行 |
| 父键不唯一的原因 | 主数据版本重复(同一工单号多次入仓) | 软删除(已删除行仍在表里) |
| 不构成关系的共享列 | 组织、公司、租户、分区列 | 企业编号(租户键) |
| 最有力的证据 | 后端数据访问层的 JOIN 条件 | 前端调用链与类别目录 |
| 原做法 | 专用脚本把表归并为概念(写死厂码与来源前缀) | 领域技能 + 构建体检 + 交叉复核 |

两边遇到的是同一个问题的两面:**表不等于概念**,以及**先定有效行,再判唯一与重叠**。
专用脚本不能复用到别的湖仓(厂码写死),能碳的做法又没有覆盖「多表一概念」。

## 决定 / Decision

### 1. 概念层线索(`concept_hints.py`,确定性、只读)

- **表族**(多表一概念):去库名前缀、数仓层级、噪声后缀(备份、离线、日期、数字变体)后,
  **从表名学习可替换的前缀**——一个词后面接的剩余部分也常出现在别的词后面,并且它后面接的表
  不少于 10 种且不少于总表数的 1%。厂码、来源约定后面接上百种表;测试类型(fct_、aoi_)只接几种,
  不会被剥掉。后缀只学数字与三个字母以内的变体标记,且排除 obj、rel、log 等业务尾词。
  站点段按「…_编号_」整段剥离。单个短词根的族另要求业务列相似度 ≥ 0.2。
  代表表取正本(无备份后缀),再按层级(明细 > 维度 > 汇总 > 贴源)、行数、列数。
- **类别拆分**(一表多概念):实例表的类别列 → 目录表(≤5000 行、编码基本唯一、带名称列、
  表名与类别列词干相符、覆盖 ≥90% 的类别值、各类名称不全相同、不是实例表的同族副本)。
- **版本重复**:业务键与表名对得上、去重后不少于 95%、表里有时间列。

### 2. 构建体检与流水线接入

- 体检报告新增三类发现、**场景画像**(湖仓:≥30% 的表属于表族;元数据驱动:存在类别拆分,两者可并存)
  与**参照 + 领域技能建议**(按占比判断领域信号,零星几张相关表不算;PCBA 信号建议电子制造技能)。
  采用建议时一并勾选领域技能。
- 分轮计划只放表族代表表,其余成员随代表表列出。
- 构建时:本轮范围内的线索放在结构文本之前给提议模型;产物生成后把同族成员表挂到同一个对象上,
  同族多对象只标注不删除。

### 3. 有效行进入交叉复核

`ontology-cross-check` 1.1 新增「有效行」通道:重叠达标却因父键不唯一被拒的候选,排除软删除行
或按键取最新(重复不超过 5%)后父键唯一的,标为「有效行成立」,送复核。

### 4. 技能分层

- 通用:`ontology-semi-auto`(证据契约)、`ontology-build-method`(新增:三层、场景画像、
  构建流程、对应规则、有效行、证据强弱与对齐)、`ontology-cross-check`(复核与清洗)。
- 领域:`energy-carbon-ontology` 1.2(流程移到通用技能,只保留领域内容)、
  `electronics-manufacturing-ontology`(新增:表族归并、工单与项目枢纽、过站—测试—返修—包装事件链、
  版本重复、类型与时点对齐、代码契约)。
- 构建台默认勾选三个通用技能;领域技能由体检建议采用。四个技能合计约 9,300 字,在 12,000 字预算内。

## 后果 / Consequences

- 电子制造元数据(2,206 表):学到的前缀为 6 个厂区码、2 种来源约定、3 个平台前缀,无业务词;
  263 个表族收编 2,004 张表,概念约 464 个;与专用脚本的 300 概念相比,两两归属精确度 0.996、召回 0.78
  (专用脚本另按泛化尾词与列相似度合并)。体检 0.2 秒;分轮计划 428 张代表表。
- 能碳实库抽样:28 个表族(副本、年分表、跨库同名表),9 处类别拆分(设备 → 电能表 / 光伏逆变器 / 流量计…,
  系统 → 子用能系统 / 用能系统 / 光伏站 / 园区),体检 0.3 秒。
- 电子制造业务采样:工单号 77 行版本重复被识别;此前被拒的「过站明细 → 工单」关系在交叉复核中
  标为「有效行成立」——此前靠手工建去重表才能通过。
- 真实模型各跑一轮(同一组通用技能 + 各自的领域技能):
  - 能碳 22 张表:34 个对象(用能单元拆为用能系统 / 子用能系统 / 园区 / 光伏站 / 储能站,计量器具拆为电能表 /
    流量计 / 蒸汽表 / 逆变器 / 变流器,能源介质以字典值为概念),两组副本表并入同一对象;已验证关系 11 条
    (此前只用通用技能 8 条、加能碳技能 4 条)。「用能单元 / 设备 → 类型目录」因软删除被拒,复核标为有效行成立。
    关联表仍有 5 张被建成对象——这是「一表一对象」的结构约束,技能改不了。
  - 电子制造业务采样 11 张表:已验证 3 条(此前同一采样无代码契约时 0 条、加后端 JOIN 契约后 5 条);
    「过站明细 → 工单」因工单号版本重复被拒,复核标为有效行成立。
- 新增单测 18 项(944 总数)。技能与模块不含任何客户、厂区或系统的具体名称。

## 备选与不做 / Alternatives

- **把专用脚本的厂码表并入平台**:不做。前缀从数据学,换一个湖仓不用改代码。
- **按泛化尾词(detail / info / base)再合并**:不做。召回会升,但会把明细与主表并为一个概念,
  错并比漏并更难发现。
- **IR 支持「行子集」对象**:本次不做。类别拆分以线索形式交给提议模型;对象级的筛选条件需要问数与
  裁决同时支持,另行评估。
- **外部 Hive/Paimon 只读抽样**:本次不做,仍需按分区对齐、类型保持字符串的方式手工物化。
