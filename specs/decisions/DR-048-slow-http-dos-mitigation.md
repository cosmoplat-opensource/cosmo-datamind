# DR-048 · HTTP 慢速攻击缓解(Slowloris)

- **状态 / Status**: accepted
- **日期 / Date**: 2026-08-14
- **决策者 / Deciders**: Boss(用户,漏洞扫描报告)+ Writer(Claude)
- **关联 / Refs**: [[DR-006-security-model]];实证=`srv_hardening.py`、`server.py`、`tests/unit/test_srv_hardening.py`、实连复现记录

## 上下文 / Context

漏洞扫描系统 2026-08-14 对 `http://192.0.2.32:8092/` 的扫描,
在 0 紧急 / 0 高危 / **1 中危** / 10 低危 / 7 信息中,唯一中危为:

| 项 | 值 |
|---|---|
| 漏洞 | http 慢速攻击(Slow HTTP DoS) |
| CVE / CVSS | CVE-2007-6750 · **5.3** |
| POC | HTTP 连接持续时间 **186s** |
| 修复建议 | ①设置适当的超时时间,规定请求头和请求体发送的**时间以及频率**;②增加最大连接数 |

该端口正是本系统。成因:`app.run()` 用 Werkzeug 内置服务器,
**请求处理器不设任何 socket 超时**、线程数无上限——只发半截请求头即可长期占用连接与线程。
本地复现:连接存活 **75s+** 未被切断。

## 决定 / Decision

新增 `srv_hardening.py`,在 `app.run(request_handler=...)` 处装上三道约束:

1. **请求头总时限**(默认 10s,`DATAMIND_HDR_BUDGET`)——克制 Slowloris(慢速请求头)。
2. **请求正文按速率判定**:初始预算 20s(`DATAMIND_BODY_INIT`)+ 每收到 500 字节兑换 1 秒
   (`DATAMIND_BODY_MIN_RATE`)+ 绝对上限 300s(`DATAMIND_BODY_BUDGET`)——
   克制 R-U-Dead-Yet(慢速请求体)。等价 Apache `mod_reqtimeout` 的 `body=20,MinRate=500`。
3. **读阻塞期间的看门狗**:读前挂、读返回即撤,超时即**主动 shutdown 连接**。
4. **socket 超时**(默认 30s,`DATAMIND_REQ_TIMEOUT`)+ **并发上限**(默认 256,`DATAMIND_MAX_CONN`,
   超出即刻关闭、不排队不占线程)——对应建议②「并发要有明确边界」。

环境变量缺失/非法/越界一律回落默认值,**不允许退化成「无限制」**。

## 三次实测才收敛的三个坑

这条漏洞的修复过程有三个各自独立、都只能靠实测才暴露的坑,依次是:

**坑一:socket 超时管不住滴入式攻击。**

首次实现只设了 `WSGIRequestHandler.timeout=30`,**实测无效**:连接每 3s 滴入一个请求头即存活 75s+。
原因是 `settimeout` 约束的是**单次**读的等待,慢速客户端持续滴入数据就能无限续命——
这正是 Slowloris 的原理,也解释了扫描器为何能撑到 186s。

真正管用的是**跨多次读的总时限**(等价于 Apache `mod_reqtimeout` 的 header 预算,
亦即报告里「时间**以及频率**」的后半句)。实现为 `_DeadlineReader`:
在 `parse_request()` 期间对读流施加绝对截止时间,头读完即换用更宽的正文预算。

**坑二:只给正文一个「宽预算」挡不住慢速正文。**
补完头预算后复测第二种变体(R-U-Dead-Yet:声明 `Content-Length: 100000` 后每秒滴 1 字节),
**存活 60s+**;而 300s 的正文预算意味着最长可占 300s,比扫描器观测的 186s 还长。
正解是报告里「时间**以及频率**」的后半句——按**最低传输速率**判定:
收到 n 字节才把截止时间延后 n/500 秒。滴入式换来的时间微乎其微,正常上传则源源不断地「挣」到时间。

**坑三:检测到了却切不断,而切得太狠又会掐死 SSE。**
速率闸触发后日志确有 `Request timed out`,但客户端**直到 70s 仍在发**——
因为 Python 3.10+ 里 `socket.timeout` 即 `TimeoutError`,被 Werkzeug 的 `handle()`
捕获后只记一行日志。且一次 `read(100000)` 会长时间阻塞,夹在读前后的检查根本轮不到执行。
于是加了「超时即主动 shutdown」+ 看门狗定时器;
但**常挂**的看门狗又在响应阶段开火,把正在推流的 SSE 打断成
`Response ended prematurely`。最终形态:**看门狗只在一次读阻塞期间生效,读返回即撤**。

**修复前后实测**:

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 慢速请求头(每 5s/3s 滴一个头)| 存活 75s+ 未断 | **10.0s 被切断** |
| 慢速请求体(每 1s 滴 1 字节)| 存活 60s+ 未断 | **20.0s 被切断** |
| 扫描器 POC | 186s | ≈ 对应阶段预算 |

## 与 SSE 长流的关系(已验证)

系统有 4 个 SSE 端点,深度问数可跑数分钟。超时是**单次 socket 读写**与**请求接收阶段**的上限,
不是响应流的寿命上限;流期间服务端只在有事件时写,客户端正常读取时写不阻塞。

实测(最终形态):一条深度问数 SSE 流 **32 个事件、历时 77.6s、最大事件间隔 34.8s
(> 30s socket 超时)完整结束**,无提前中断。
中间版本曾因看门狗常挂而把 SSE 打断,已由 `test_watchdog_idle_when_not_reading` 锁住。

## 影响 / Consequences

- (+) 中危漏洞闭环:慢速连接由「无限占用」变为 ~10s 内被切断,且并发有硬上限。
- (+) 参数全部可经环境变量按部署环境调整,启动横幅如实打印生效值供运维核对。
- (−) 头预算 10s 对**极端劣化网络**下的正常客户端偏紧;可用 `DATAMIND_HDR_BUDGET` 放宽(上限 30s)。
- **边界**:本修复加固的是内置服务器。对外提供服务时仍建议按 README 走 WSGI + 反向代理,
  由反代承担 TLS、限速与更强的连接治理——本修复保证的是**即便直接暴露内置服务器也不再被慢速攻击拖垮**。
