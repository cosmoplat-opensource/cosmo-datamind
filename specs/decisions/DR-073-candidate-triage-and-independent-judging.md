# DR-073 · 候选关系分流、问数选表修正与澄清、抽样截断标记与独立评审

- **状态 / Status**: accepted
- **日期 / Date**: 2026-10-03
- **关联 / Refs**: [[DR-072-whole-dataset-evaluation]]、[[DR-067-scenario-regression-benchmark]];
  实证=`tests/unit/test_build_agent_gaps2.py`、`tests/scenarios/bench.py`

## 上下文 / Context

DR-072 的全库评估留下四个问题:

1. 候选关系 336 条,是人工审阅的大头,其中多数凭已有证据就能判定不成立;
2. 问数在若干同类表(两套巡检、几套标签、几套账单)之间仍会选错表;
3. 部分关系因孤儿记录停在候选,拦下了问数(账单明细 66% 的账单编号在账单表中找不到);
4. 评估本身有边界:数据是抽样(大表只保留最新 2 万行)、只有一人判定真伪、只在能碳一个库上测。

## 决定 / Decision

### 一、候选关系分流(`relation_triage.py`)

裁决与交叉复核之后、产物落盘之前,对每条候选只用已记录的证据(重叠率、父键唯一、键名依据、复核结论、字段类型)
分成三类,不调模型、不查库,可回放:

- **自动驳回**:重叠率低于 20% 且键名不直接指向父表;交叉复核强冲突(原裁决未验证);同一子键已验证指向更贴切的父表;
  键名无据且父键不唯一或重叠不足;键名无据的整数键(自增 id 值域天然重合);审计列(含复合键中的审计列);
  父键不是父表的标识(企业编号指向任意带该列的表,这是共享列,不是引用);实例表而同名目录表才是定义。
- **暂缓**:两端表在抽样中没有数据;或键名直接指向父表的标识(`flow_id → energy_flow.id`、`produce_code → produce.produce_code`)
  但抽样中重叠很低——两表各自只留最新数据时,重叠低不能证伪,需全量数据核对。
- **待审**:其余候选,按「重叠率 × 键名依据 × 父键唯一 × 方向」计分排序,并写明还缺哪一项证据。以下几类不驳回而进待审:
  编码列取值落在目录表自身编码内(`metrics_type → meta_device_type.dev_type_code`);主从表同名键
  (`pv_report_detail.report_uid → pv_report.report_uid`,父表重复行多是版本);原裁决已验证、键名有据,
  只是交叉复核发现疑点(名称快照不一致等)。

驳回与暂缓的条目移到 `rejected_relations` / `deferred_relations`,保留原证据与理由,可追溯、可恢复。

### 二、关系判定补强

- **自引用**:`parent_id`、`ReportsTo` 等指向本表主键的关系可提议、可验证(子键与父键不同列)。
- **以父表命名的 id 引用容忍孤儿**:`statement_info_id → statement_info.id` 这类子键词根就是父表核心名的引用,
  孤儿记录多时仍验证并记录孤儿率,问数时按孤儿率提示,不再停在候选拦下问数。
- **词元前缀缩写**:`anal_obj_id → analysis_object.id`(每个词元至少 3 个字母、依次是父表名相邻词元的前缀),
  命名判定与交叉复核的自增 id 碰撞通道同口径。
- **抽样截断标记**:库表估计行数(`_dm_tables.rows_est`)超过抽样行数 5% 以上的表,其上的关系标记 `sample_limited`,
  重叠不足的候选不据此驳回,待审理由写明「全量数据核对」;另附只读复核脚本,在可连实库时按全量数据重算这些关系。

### 三、问数选表修正与澄清

问数生成的 SQL 所查的表与问句提到的业务对象不一致时,带着「表与问句对象不一致」的修正要求重新生成一次;
仍不一致,或关系门禁拦下且没有其它可用结果时,不给答案,而是列出候选表(附已验证关系数)请用户指明。
复用技能的 SQL 只做观察(DR-026),不在此处丢弃。

六次问数中选错表的都带了提示或转为请用户指明,没有静默答错。

### 分流的准确性:独立评审

为避免只有一人判定,另请两位互不知情的评审在同一抽样库上盲评 270 条(已验证 60、自动驳回 40、待审前 30、
全库穷举候选 140,随机编号、不给系统结论):

- 两位评审一致 99%(κ = 0.98);在穷举候选上与原人工判定各一致 98%(κ = 0.92);
- 已验证 60 条:两人都判真 59 条;待审前 30 条:真 22~23 条;
- 自动驳回 40 条:初版规则下两人都判真 9 条,据此修正了四类误驳回(键名直指父表而抽样无匹配、编码列落在目录表编码、
  主从表同名键、已验证关系的复核疑点),修正后 40 条中只剩 1 条(两字母缩写);
- 为检验修正是否只对评审样本有效,对规则修正后改变分类、且不在评审样本中的 25 条,再请第三位评审盲评:
  判真的 18 条无一被驳回(待审 9、暂缓 9),被驳回的 4 条全部判假;另 3 条判假的进了暂缓(全量核对时会驳回)。

### 仍未解决

- 抽样数据:暂缓的 74~86 条需全量核对;只读复核脚本已备好,但实库需内网连接,本次未能执行。
- 概念命名不稳(见上),是问数剩余错误的主因。
- 名称不同的角色键(ShipVia、SupportRepId、两字母缩写 gd_id)不提议。

## 备选与不做 / Alternatives

- **按固定重叠阈值一刀切驳回**:不做。键名直指父表的引用在抽样中常因两表各自截断而重叠很低,独立评审确认其中多数为真;
  这类改为暂缓,由全量核对决定。
- **交叉复核冲突一律驳回**:不做。原裁决已验证、键名有据时,冲突多为名称快照变化等疑点,交人审。
- **两字母首字母缩写(`gd_id → gateway_dtu`)**:不做。误配风险高,保留为已知漏判。
