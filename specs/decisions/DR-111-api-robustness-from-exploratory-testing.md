# DR-111 · 探索性测试查出的后端缺陷

状态：已实现。日期：2026-11-14。
关联：API-ROBUST-01、UPLOAD-02、DR-006。来源：对 128 条路由的畸形请求测试和上传、查询、SPARQL、构建作业的专项测试。

## 问题与处理

**查询结果没有大小上限。** 一条 `SELECT hex(zeroblob(200000000))` 返回 400 MB。行数有上限、长查询会中断，但单个值不受限。
现在只读连接上单个值超过 10 MB 由引擎报错；返回时单元格超过 2 万字符截断并注明原长，响应里的 `truncated_cells` 给出截断的格数。
二进制列转成十六进制文本返回。

**入参类型不对时返回 500。** `graph`、`key`、`id`、`base_graph` 传成列表或对象时，路由里的正则和字典查找直接抛异常。
现在这四个标识字段在进入路由前统一校验，类型不对返回 400；`/api/ont/apply` 的 `op` 不是对象时返回 400。
另加一层兜底：接口的未预期异常统一返回 JSON 的 500，细节只写日志，不回给调用方。

**上传不认常见的中文文件。**

| 此前 | 现在 |
|---|---|
| GBK 文件报 Python 的解码错误 | UTF-8 解不开时按 GB18030 读，返回里注明编码 |
| 分号分隔的文件被导成一列 | 表头里没有逗号时按分号、制表符、竖线试，各行列数一致才采用 |
| `订单 表(1).csv` 的表名是 `_____1_` | 表名保留中文（`订单_表_1_`）。纯英文文件名的表名不变 |
| 所有列都是文本 | 逐列判型：非空值全是整数为 INTEGER，全是数值为 REAL；带前导零的编码、超长数字串保持文本，数值列的空格存 NULL |
| `.xlsx` 等文件被保存但没有任何说明 | 返回 `notes`，说明已存档、未建表；构建页的提示里带出 |
| 列太多、编码无法识别时报引擎或 Python 的原始错误 | 给出可操作的中文说明 |

表名规则变了以后，升级前按旧规则建的中文文件名的表在删除资料时一并清掉（前提是没有别的资料在用那个名字）。

**SPARQL 的 ASK 与 CONSTRUCT 结果不对。** ASK 返回一行空对象，CONSTRUCT 返回空行，类型都标成 SELECT。
现在 ASK 返回 `boolean`（并给一行「是 / 否」供表格显示），CONSTRUCT / DESCRIBE 返回主、谓、宾三列。

**无效的构建请求也建作业。** `POST /api/build/jobs` 在诉求为空或数据源不存在时先返回 202、作业随后报错。现在直接返回 400。
流式接口 `/api/build/inquire` 不变，界面靠流里的错误事件显示原因。

**没有安全响应头。** 所有响应带上 `X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、
`Referrer-Policy: same-origin` 和 `Content-Security-Policy: frame-ancestors 'self'`。页面大量使用内联事件处理，
内容安全策略暂时只限制嵌入方。

**示例图谱过不了自己的质量闸。** 随仓分发的「示例企业本体」（`built_2d74f0`）是早期构建的，104 条 verified 关系
没有记录父键唯一和键名证据，质量闸有 136 条阻断。对示例库逐条重新取证（与构建同一套裁决规则）：100 条保持 verified 并补齐证据，
4 条证明不了的降为候选（3 条键名词根不一致，1 条子键只有一个取值）。质量闸结果由不通过变为待评审。

## 没有改的

- 另有 6 张随仓分发的历史构建产物同样过不了质量闸，处理见 DR-113。
- 内置「应用本体」的 149 条 SHACL 违反是对象缺定义，补定义需要模型。
- 模型离线时在已有图谱上继续构建，仍会走数据驱动降级并并入结果。是否改成直接停下由使用者决定。
