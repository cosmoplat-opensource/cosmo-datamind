# DR-074 · 本体删除恢复与历史保留

- **状态 / Status**：proposed（待方案评审）。
- **日期 / Date**：2026-11-12。
- **关联 / Refs**：[IR-028](../iterations/IR-028-ontology-asset-lifecycle.md)、[总方案](../../docs/datamind-application-contract-design.md)。

## 上下文 / Context

旧数据构建有 /api/build/delete，直接删除 built_*.json；机器人注册资产无对应统一删除入口。现有删除对象／关系与整份资产删除不同。

## 决定 / Decision

以下为建议方案，用户方向已明确，具体接口和取舍仍待评审。

1. 第一版提供逻辑删除和恢复，资产状态 active／deleted 与版本发布状态分别存储；页面明确说明从目录和应用选择中移除但保留历史，不承诺物理擦除。永久清理和留存期限另行设计。

2. 删除前展示版本数量、来源、任务／运行和历史引用影响。共享来源、不可变版本、设计修订、历史结果保留；历史链接显示已删除标记。禁止据已删除资产发起新构建、适配或任务。

3. 存在 queued／running 设计、构建、适配或生成时返回 conflict，用户在完成后重试；删除与运行受理在同一存储锁和事务边界复核，消除先检查后排队竞争。等待输入的会话删除后冻结写入，恢复后重新检查版本和配置。

4. 使用资产修订／ETag、幂等 request_id 和审计记录。删除预览返回影响摘要，提交必须带同一 revision；依赖变化时要求刷新。恢复不恢复旧 ready 缓存或失效证据。

5. 兼容旧 built key：先固定有效 IR 与编辑层、建立 alias 和 tombstone，再从所有目录／build、问数、任务入口过滤。旧 /api/build/delete 委托统一服务；禁止原始文件扫描重新登记已删除资产。demo 和内置只读资产受保护。

6. 明确数据库迁移、文件操作和缓存失效的顺序；以事务状态为准，文件原样保留降低跨文件原子性风险。删除当前 UI 选中版本时清理选择，禁止错误地跳到另一份本体。

## 后果 / Consequences

可与 IR-026 并行；IR-025 提供执行前生命周期检查接点，IR-027 配合旧 graph key。
需要版本化检查和修复记录，增加维护成本；换取构建自由、应用诊断和执行一致性。
不改变 IR-024 已交付范围，按新迭代实现并回归。
