# DR-067 · 场景回归基准:两种数据形态端到端比对标准答案

- **状态 / Status**: accepted
- **日期 / Date**: 2026-10-01
- **关联 / Refs**: [[DR-064-unified-method-across-scenarios]]、[[DR-065-end-to-end-parity-code-contracts-and-scoped-keys]]、
  [[DR-066-ai-era-development-paradigms]];
  实证=`tests/scenarios/fixtures.py`、`tests/scenarios/bench.py`、`tests/scenarios/test_scenarios.py`、`scripts/scenario_bench.py`

## 上下文 / Context

DR-063…065 期间发现的缺陷包括:问数计数翻倍(关联缺租户条件、未排除已删除行)、口径校验误拦已验证关系、
模型超时后兜底构建全库、上传的代码包未被读取、构建流中途因变量名覆盖而中断。这些缺陷都是用真实数据
端到端运行、再把答案与直接查库的结果比对时发现的。当时靠人工重跑、人工核对数字,每轮十几分钟且依赖模型。

单元测试覆盖各模块的局部行为,发现不了「各模块单独正确、组合后出错」的问题。

## 决定 / Decision

把「端到端跑 + 与标准答案比对」做成随每次提交运行的基准:

- **两个合成库**(`fixtures.py`),各对应一种数据形态,预置实测中遇到过的问题:
  - 多厂多层湖仓:同一实体的多厂副本、区域编号按工厂复用、工单号版本重复、字典编码按分组复用、
    两张无关表的自增 id 碰巧重叠、键名不同但代码里写着连接、字段含义只写在代码注释里;
  - 元数据驱动业务库:设备表按类别装着多种概念、类型目录里同一编码有已删除行、计量关系大量悬空引用。
  标准答案在生成数据时直接计算,不经被测代码。
- **全走真实代码路径**(`bench.py`):登记数据源 → 构建体检 → 上传代码包 → 构建(含交叉复核)→ 问数,
  全部经 HTTP 接口。只把调用模型的四处换成固定输出:抽取返回一份「录制」的提议,语义评审返回不可用,
  意图解析与生成说明返回固定文本;问数的 SQL 也由固定输出给出,一条缺少必要关联条件,一条正确。
- **检查 23 项**:体检判断、表族与类别拆分、代码契约读取与字段中文名、每条关系的最终状态与有效行规则、
  缺陷前提成立(直接执行错误 SQL 计数确实翻倍,以此确认基准本身有效)、错误 SQL 被口径校验拦下、
  正确 SQL 的答案与标准答案一致、问数在来源库上执行、兜底构建只建本轮范围。
- `pytest tests/scenarios` 随单元套件运行(约 1 秒);`python3 scripts/scenario_bench.py` 逐项打印检查结果。

## 后果 / Consequences

- **首次运行检出一个缺陷**:代码里的表名(`t_line_zone`)按「最长后缀」匹配,只对上了保留 `t_` 约定的
  贴源副本,漏掉维度表与明细表——带多厂副本的湖仓里,代码契约与字段含义会挂到错误的表上。
  DR-065 在真实业务采样上没暴露,因为那个样本库里恰好没有贴源副本。已修正为「更短的后缀覆盖整族时取整族」,
  并在真实代码与样本上确认结果不变(6 条连接、3 条码表)。
- **变异验证**:把 DR-063…065 修复过的 6 个缺陷逐个恢复,基准均能检出:兜底构建全库、口径校验只认示例本体的
  关系形状、问数不检查租户作用域、上传的 zip 不读、构建流变量名覆盖、软删除条件不进问数。
- 基准不连模型,因此不衡量模型提议的质量;模型相关的回归仍需用真实数据抽查。

## 备选与不做 / Alternatives

- **用真实客户数据做基准**:不做。不能进仓库,也不能在 CI 里访问;合成库按真实形态构造,名称中性。
- **把模型输出也纳入基准(录制-回放多种提议)**:暂不做。当前只录一份理想提议,检查的是提议之后的确定性链路。
