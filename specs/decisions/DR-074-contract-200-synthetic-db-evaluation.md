# DR-074 · 200 表合成验证库评估:星型模型键名、字段注释证据与几类误判

- **状态 / Status**: accepted
- **日期 / Date**: 2026-10-03
- **关联 / Refs**: [[DR-073-candidate-triage-and-independent-judging]]、[[DR-070-orphans-scoped-codes-codebooks-kinds]];
  实证=`tests/unit/test_build_agent_gaps2.py`、`tests/unit/test_build_prep.py`

## 上下文 / Context

`scripts/build_contract_200_db.py` 以 108 表演示库为底(只读)合成 200 表验证库:新增 92 张表(67 张事实表、25 张维表),
5,598 列,476 个声明外键,库内带完整的表/字段中文元数据(`dim_table_metadata` / `dim_column_metadata`)。
构建智能体不读声明外键,声明外键可直接作盲测参考答案。评估前对库本身做了检查:

- **声明外键不完整**:原 108 张表的大部分引用(设备→产线、物料→供应商、仓库→工厂等 71 条)只写在字段注释里
  (「外键,关联 dim_x」),没有声明。参考答案取声明 476 条 + 注释写明 71 条,共 547 条(543 个表对)。
- **注释与数据不一致**:`fact_downtime.reason_code` 注释说关联停机原因表的 `reason_code`(D001…),
  实际存的是 `reason_id`(1~8);参考答案按数据改正。
- **汇总层与明细层不一致**:设备日汇总的报警数合计 544,报警明细只有 121 条。
- **新表是模板化数据**:87% 的新表外键按轮转均匀引用(引用次数变异系数中位数 0);无孤儿、无逻辑删除;
  租户、来源系统、创建人、质量分整列恒定;主数据的创建时间全是生成时刻(晚于业务日期)。
  新表平均 51 列,大半是模板公共列。该库主要检验结构与命名识别,检验不到脏数据(孤儿、软删除、版本重复)。
- **整数 id 高度重合**:169 张表的整数主键都从 1 开始;一个整数外键的子列值域中位数被另外 119 张表的主键完全覆盖,
  取值重叠对整数键几乎没有区分力,只能靠键名与注释。

第一次构建(修改前):对象 199、已验证关系 272,参考关系召回 42%;14 道问数 3 次全对。

## 发现与决定 / Findings and Decision

召回低与误判的原因都在通用规则,不是这个库特有:

1. **星型模型的码值维度与日历维度不提**:`reason_code → dim_reason_code.code`、`currency_code → dim_currency.code`
   的父键是泛化列 `code`;`business_date → dim_calendar.calendar_date` 是日期列。266 / 270 条没有提出。
   补:父键为 `code` 时子键词根与维表核心名相符即提(`reason` ↔ `reason_code`、`unit` ↔ `unit_of_measure`);
   日期列取值落在日历表日期键中(≥ 60%)即提,命名判定同步认可。父表有多列都像标识(`currency_id` 与 `code`)时取重叠最高的一列。
2. **`fact_` 前缀没剥**:学到的表名前缀里 `fact_` 被当作子类型保留,事实表核心名错(`fact_sales_order`)。
   提议时再剥一次数仓分层前缀(fact/dim/dws/ods/dwd/ads/dm);`meta_`/`inst_` 区分目录与实例,不剥。
3. **工厂键一律当租户键**:租户键「只在关联表上提」改为只对铺满全库(四分之一以上的表都有)的键生效;
   被压下的租户键也不退而连到「企业-位置」关联表。
4. **泛词词根不算标识**:`order_id`、`type_id`、`level_id` 的词根在泛词表里,永远不提。
   改为泛词词根是父表核心名末词时算标识(sales_order.order_id、equipment_type.type_id)。
5. **字段注释没有用作证据**:
   - 注释写明「外键 / 关联 / 引用 dim_x」且表存在时,作为连接契约:与代码契约同等,可替代键名依据,数据门槛不变;
     注释只点名表,父列由数据选。
   - 多张父表名称并列时(`line_id` 是产线表与采购订单行表的标识),字段注释含哪张父表的中文名就取哪张(「产线ID」→ 产线);
     名称仍并列时看取值,只有一张父表装得下子列取值就取它。
   - 注释的中文名就是某张父表的中文名(「所属业务单元ID」→ 业务单元表)且取值落在其标识中,补提(缩写 `bu_id` 对不上时)。
6. **几类误判**(盲评发现):
   - 子表自己的主键对上另一张表的主键(单据头 → 明细的主键、`payment_out.payment_id → payment`):两个主键值域碰巧重合。
     子键词根就是子表核心名、父键是另一个名字时不算键名依据;孤儿容忍只给非主键的引用列。
   - 同名共享列:模板列 `legacy_code`、明细表里的 `order_id`、同粒度汇总表的 `(date, dim_emp_id)` ——
     父表不拥有该列且该列出现在 3 张以上的表时,同名不算依据。
   - 反向修饰:`line_id → cycle_count_line_id`(父键是更具体的概念);序号对标识:`line_no → line_id`;
     父键有自己的具体词根而与子键无关时(`supplier_id → eval_id`),不凭「子键词根出现在父表名里」认定。
   - 同一列对自己(`category_id → category_id`)不是自引用;子表主键(首列)不按「实例 → 目录」提。
7. **复核与体检的误报**:主数据的时间列整列只有一个值(装载时间)时,时间先后通道不判,原先 308 条弱冲突全是这个;
   体检把经数据验证的层级自引用(`parent_id → category_id`)当成自反错误,改为子父键不同列即豁免;
   类别作用域复合键不再把度量列(时长、数量、金额)当作用域列。
8. **临时表误排除**:注释含「临时用电」的作业许可表被当作临时表排除。注释只认「临时表 / 测试数据 / 演示用」这类词组。

## 后果 / Consequences

### 200 表合成验证库(5 轮,真实模型,通用技能,不带行业参照)

参考答案 547 条(声明 476 + 注释写明 71,按数据改正 1 条);金标外的已验证关系分两批请互不知情的评审盲评
(只看库与中英文元数据,不看声明外键,也不知道系统结论),判真的计入正确。

`line_id` 注释误写成「明细标识」;`source_cc_id` / `target_pc_id` 这类缩写),留给模型与人工。

### 仍未解决

- 能碳问数剩余错误仍是概念命名不稳(「标签」「用能单元」「设备类型」选到同名的另一张表),本次没有处理;都转为提示或请用户指明。
- 合成库是模板化数据,孤儿、软删除、版本重复等脏数据规则在这个库上测不到。

## 备选与不做 / Alternatives

- **读库里的声明外键**:不做。实际业务库多数不声明外键(能碳无一条),声明外键只作评估参考答案。
- **把度量层与明细层的不一致当作智能体错误**:不做。报警数按日汇总层与按明细计数都有数据依据,问数评估两种口径都认;
  不一致本身是该库的数据问题。
