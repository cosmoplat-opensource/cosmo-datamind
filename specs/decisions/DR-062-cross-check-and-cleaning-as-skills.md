## 上下文 / Context

DR-061 提出三项流水线结构调整(概念层先行、关系经由关联表表达、多通道裁决),状态为 proposed。
复核中还发现编码冲突、标错的编码、悬空引用、迁移空壳等数据问题,原打算整理成清单交给平台方。

两点判断:

- 这些调整大多是「每一步该做什么」,属于方法,适合写成技能;技能可编辑(DR-051)、随仓分发、
  按领域组合,比把方法写死在流水线里更容易演进。
- 编码冲突、悬空引用在业务库中反复出现,每次靠人反馈不可持续。智能体应当自己通过清洗与
  交叉验证处理:识别问题、给出带证据的处理规则,并在取数与复核时套用。

## 决定 / Decision

### 1. 流程映射进领域技能

`energy-carbon-ontology` 1.1 新增「构建流程」一节,逐步对应平台已有的环节:
体检(构建体检)→ 分流(两个行业参照)→ 概念层 → 映射(分轮构建)→ 裁决 → 交叉复核与清洗 → 桥接与验收。
技能正文进入构建提示词,影响提议;确定性的检查由下面的可执行技能完成。

### 2. 新增可执行技能 `ontology-cross-check`

正文(进入提示词)约束提议:不提无名称证据的 id 对 id 关系、租户键不逐表提议、多态引用写明判别条件、
同一对表只提一个方向。`run.sh` 对构建产物做构建后复核,只读、只用标准库、不改原文件:

- **关系复核**:冗余名称、自增 id 碰撞为强冲突;双向验证、软删除、时间先后为弱冲突;另标租户键、
  按判别值分条件比对未通过的候选。`--apply` 只把强冲突降为候选,原裁决保留在 `evidence.cross_check`。
- **数据清洗**(`--clean`):码表判定(字典表与字段注释,按取值覆盖率与名称相似度)、
  同名字段的编码冲突与码表对照、按实体类别检测离群编码(可沿关系取父表类别)、
  悬空但语义成立的关联、悬空引用比例、迁移空壳、注释编码不符。
  产出声明式规则(证据 + 建议动作 + 清洗视图 SQL 片段),挂到对象的 `evidence.cleaning`。

核心流水线(`_adjudicate_ir` 的裁决口径)不变。

## 后果 / Consequences

在能碳实库抽样(496 条关系,240 条已验证)上运行约 20 秒:

| 结论 | 数量 |
|---|---|
| 强冲突,降为候选 | 9(自增 id 碰撞 8、名称不一致 1) |
| 弱冲突,送复核 | 8 |
| 有独立证据支持 / 仅单通道 | 99 / 114 |
| 租户键 | 62 |
| 按条件成立的候选 | 14 |
| 清洗规则 | 编码冲突 37、离群编码 3、悬空但语义成立 3、悬空引用 76、迁移空壳 9、注释编码不符 84 |

- 计量关系指向设备的一侧重叠率只有约 11%,原本停在候选;清洗发现设备类别仍以 0.94 的一致率
  决定能源类型,判定为「悬空但语义成立」,并找出被标成其他能源的电能表行。
- 电价分组表的注释码表只能解释 86% 的取值,数据实际使用主字典;注释记为有误。
  这与此前只看注释得出的判断相反,说明码表要由数据判定。
- 新增单测 11 项(916 总数)。技能与脚本不含任何客户或系统的具体名称。

## 备选与不做 / Alternatives

- **直接改裁决器**:不做。裁决口径改动影响所有已有产物,需要单独评估误判与漏判;
  技能先以复核与清洗规则的形式落地,口径稳定后再考虑并入。
- **自动更正源库**:不做。源库只读;更正只在清洗视图中生效。
- **构建结束自动运行复核**:暂不做,由使用者或智能体按技能说明调用 `run.sh`。
- **概念层先行、关系经由关联表**:已写进领域技能的流程与规则,由提议阶段执行;
  流水线的「一表一对象」结构性约束仍在,待后续评估。
