# DR-024 · 能力问题(CQ)驱动的本体构建与验收

- **状态 / Status**: accepted
- **日期 / Date**: 2026-08-02
- **关联 / Refs**: [[DR-002-multimodal-llm-anti-hallucination-build]]、[[DR-011-generalized-adjudication]]、[[DR-019-deepqa-upgrade]](问数评测);外部依据见下

## 背景 / Context

《本体智能研究报告(1.0)》(人工智能产业联盟 AIIA × 大数据技术标准推进委员会 CCSA TC601,2026)
在「六阶段落地流程」中把**能力问题(Competency Questions, CQ)**放在阶段一与阶段四两处:

- 阶段一(领域理解与需求分析):"定义能力问题,即本体建成后应能回答的问题集合";
- 阶段四(验证与质量评估):"将阶段一定义的能力问题转写为针对真实样本数据的查询,
  检验本体在实际数据上的回答准确性,**这是验证本体是否真正可用的核心环节**"。

对照本系统现状:我们有 `/api/ont/completeness` 完备度记分卡(定义/反例/接地/成熟度覆盖率)、
有 `/api/eval/*` 问数评测(8 题参考基准 × 三组对照),但两者都**不是 CQ 验证**:

- 完备度记分卡度量的是**本体自身的形式完整性**(有没有定义、有没有接地),
  它回答"本体建得规不规范",回答不了"本体够不够用";
- 问数评测度量的是**问数链路的端到端正确率**,题集独立于本体构建过程,
  且混杂了 SQL 生成能力,无法归因到本体结构缺陷。

结果是:构建完成后没有一个环节能回答**"这个本体到底能不能支撑当初要解决的业务问题"**。
一个对象定义 100%、接地 100% 的本体,完全可能缺了业务真正要问的那条关系——
记分卡满分,业务却答不了。这正是报告强调 CQ 是"核心环节"的原因。

## 决定 / Decision

引入 **CQ 作为构建的输入与验收的判据**,贯穿构建前后:

1. **建前声明**:构建任务可附带 CQ 清单(自然语言问题 + 期望涉及的对象/关系)。
   CQ 不参与 LLM 提议(避免"照着答案建",污染反幻觉裁决),仅作为验收基线留存。
2. **建后核验**:对每条 CQ,在**产出的本体上**做**结构可达性判定**——
   问题涉及的对象是否都在本体中、连接它们的关系路径是否存在且状态足够
   (`verified`/`asserted` 可用,`candidate`/`gap` 记为不可靠)。
3. **产出 CQ 覆盖报告**:每条 CQ 给出 `answerable` / `partial` / `unanswerable`,
   并对不可答者指出**缺什么**(缺对象 X、缺 A→B 关系、路径仅经 candidate 边)。
4. **缺口回流**:不可答的 CQ 直接进 `gaps` 清单,成为下一轮构建/人审的工作项。

## 为什么这样做 / Rationale

- **判定必须是确定性的,不能问 LLM"能不能答"**。让模型自评会把"看起来能答"当成"能答",
  正是本系统一贯反对的臆造。改为在 IR 上做图可达性计算:对象在不在、路径通不通、
  边的状态够不够——每个结论都可回放、可解释、可追责,与数据裁决同一套认识论。
- **CQ 不进提议环节**是刻意的。若把 CQ 喂给抽取提示词,模型会倾向于"造出"能答 CQ 的关系,
  而这些关系未必有数据支撑——那会让 CQ 从验收判据退化为作弊题库,
  同时污染 `verified` 的含义(见 [[DR-002-multimodal-llm-anti-hallucination-build]] 的反幻觉规范)。
- **区分 partial 与 unanswerable 有实际价值**:前者说明本体骨架对但证据不足(去补数据裁决),
  后者说明建模漏了概念(去补抽取)——两类缺口的修复动作完全不同,合并上报等于不上报。

## 影响 / Consequences

- 构建产物新增 `cq_report` 段;`gaps` 新增 `type: "cq_unanswerable"` 条目。
- 未提供 CQ 时行为完全不变(不强制,不影响既有构建路径)。
- CQ 覆盖率成为比完备度记分卡更贴近业务的**可用性**指标,但**不替代**记分卡:
  前者答"够不够用",后者答"规不规范",两者正交。

## 代价与边界 / Trade-offs

- 可达性判定基于**当前 IR 结构**,不执行实际查询。因此它能证伪("这条路径不存在,必然答不了"),
  不能证成("路径存在"不等于数据里真有值)。**这个边界必须在报告里如实标注**,
  不能让 `answerable` 被误读为"已验证可答"。真正的数据侧验证由 `/api/eval/*` 承担,两者互补。
- CQ 的对象指涉依赖名称匹配(中英文名/表名/别名),存在漏匹配可能;漏匹配一律**从严**
  判为 `unanswerable` 并注明"未能锚定对象 X",宁可误报缺口,不可漏报缺口。
