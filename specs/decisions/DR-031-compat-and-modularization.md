# DR-031 · 向后兼容性检查与本体模块化

- **状态 / Status**: accepted
- **日期 / Date**: 2026-08-02
- **关联 / Refs**: [[DR-030-ontology-health-check]]、[[DR-028-rules-and-decision-layer]](规则消费者)、[[DR-015-palantir-actions]](动作消费者)

## 背景 / Context

第四遍对照《本体智能研究报告(1.0)》时找出三处空白,DR-030 做了异常关系检测,
本轮补齐剩下两处:

| 报告要求 | 出处 |
|---|---|
| 本体版本管理与**向后兼容性保障** | 阶段六「持续维护与演化」 |
| **模块化策略**(按领域或按层次拆分) | 阶段二「本体建模的关键决策」 |

**兼容性**:本体是**语义契约**——问数靠它召回表与口径、规则靠它锚定对象、
动作靠它绑表、穿透链路靠它连通。改本体不是改一份文档,是改一份被多方消费的契约:
删掉一个对象,可能让几条规则永不触发、几个动作绑不到表,而这些往往**直到线上报错
才被发现**。

**模块化**:我们的本体是一张平图,108 个对象平铺没有模块边界。后果很具体——
改一处不知影响范围、想按域交给不同团队维护无从下手、新人打开图谱看到 108 个节点
建立不了认知。报告在五大价值里也点到:"只需更新相应的**本体模块**,而无须重新
训练整个 AI 模型"。

## 决定 / Decision

1. **`compat_check.py` + `GET /api/ont/compat/<key>`**
   比较基线 IR 与当前编辑后 IR(或 `?against=<另一图谱>`),分三级:
   `breaking`(删对象/删关系/改绑表/删属性)· `risky`(状态降级/删别名)· `safe`(纯新增或状态升级)。
   **重点是下游影响**:变更命中了哪些已注册的规则、动作、沉淀技能。

2. **`module_split.py` + `GET /api/ont/modules/<key>`**
   两种策略对应报告的两种拆法:
   `by_domain`(连通分量 + 词根聚类)· `by_layer`(数仓分层语义)。

## 为什么这样做 / Rationale

- **下游影响是重点,不是附赠**。只报"删了 3 个对象"没有决策价值;
  报"删掉的 `fact_sales_order` 上挂着 2 条审批规则和 1 个动作"才让人知道该不该删。
  我们恰好有现成的消费者注册表(规则的 `on`、动作的 `object_table`、技能 SQL 的表名),
  不用额外埋点就能算出影响面。
- **不阻断变更**。兼容性是**决策依据,不是权限**——强行拦截会让紧急修正也做不了。
  系统负责让人看清代价,判断权在人。
- **模块化只建议,不落盘改结构**。模块边界最终是业务决策(哪些概念属于"销售域"
  要业务说了算),算法只能给出结构上的自然分界供人调整。
  **自动切分会把一个错误的边界固化进本体**,比不切更糟。
- **模块划分不调 LLM**。让模型"猜"领域归属会产生看似合理实则随意的结果,
  且同一本体两次调用可能不同——模块边界必须**稳定可复现**。
- **孤岛单列**。不参与任何关系的对象无法由连通性归组,强行塞进某模块是编造。

## 影响 / Consequences

- 发布本体变更前可先看兼容性报告,把"改了会坏什么"从线上事故提前到评审环节。
- 模块化给出可交付的域划分:`by_layer` 得到维度层 44 / 事实层 48 / 汇总层 15 / 聚合层 1;
  `by_domain` 得到 7 个域(production 域 40、maintenance 域 9…)。

## 代价与边界 / Trade-offs

- 兼容性检查只看**结构与已注册消费者**。人工写在外部系统里的 SQL、
  下游 BI 报表对本体的依赖,系统看不见——这类依赖只能靠人工评审补充。
- `by_domain` 的模块名取自主词根(如 `production域`),是**机械命名**,
  多半需要业务改名。内聚度字段(主词根占比)用来提示这个名字有多可信。
- 模块划分的质量**受限于关系完备度**:实测 demo 本体 50/108 是孤岛,
  `by_domain` 因此主动警告"孤岛过多时模块边界不可信,先补关系再谈模块化"。
  这与 [[DR-030]] 健康度体检的发现一致——**两个独立检测指向同一个建模短板**,
  互为佐证。
