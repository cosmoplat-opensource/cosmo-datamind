# DR-033 · 选中的本体图谱成为问数的锚定源

- **状态 / Status**: accepted
- **日期 / Date**: 2026-08-02
- **关联 / Refs**: [[DR-032-qa-anchor-visualization]](锚定可视化)、[[DR-022-two-hop-join-path]](两跳链)、[[DR-026-double-blind-intent]](实际命中)

## 背景 / Context

DR-032 把锚定画了出来,但用户提出:**选了本体图谱之后,智能体到底怎么用这套本体,
还是看不见**。顺着这句话查代码,发现看不见是因为**它压根没发生**:

| 环节 | 实际行为 |
|---|---|
| `build_context` | 恒 `load_ir_edited("demo")` —— 无论选哪个图谱 |
| 口径校验 `ir_gate` | 恒 demo |
| 使用度埋点 | 恒记在 demo 名下 |
| 选中的图谱 | 只被展开成**表名列表**,当过滤器用 |

后果分三层:

1. **选了自建本体,用的还是示例本体的关系**。选 `built_9c3fd1`(19 对象/16 关系),
   JOIN 依据全部来自 demo 的 60 条关系;这套本体自己的关系一条都没用上。
2. **选中的图谱若与 demo 无表交集,选择等于空操作**。`cq`(上游引擎构建,5 个对象)
   的表在 demo 里一张都没有 → 过滤器命中 0 → 静默回落到 demo 全库召回。
3. **图谱内没有锚定,只有倾倒**。过滤器命中时把**全部**匹配对象塞进上下文:
   选 demo 图谱 = 108 张表全喂给引擎。这不是锚定。

再往下挖一层,发现自建本体即使被正确读取也用不了:
`_join_hints` 只认示例 IR 的 `links[source/target]` 与对象 `id`,
而构建产物用 `relations[source_concept/target_concept]` 与对象 `name` ——
**对构建产物恒返回 0 条 JOIN 提示**。而且构建器算出了父子键,却只把它写进 `note`
自由文本,没落成结构化 `evidence`。

## 决定 / Decision

1. **`_anchor_ir(graph_keys)`:选中的图谱就是锚定本体**(多选合并,未选用 demo)。
   `build_context` / 口径校验 / 使用度埋点全部改用同一套。
2. **区分「选表」与「选本体」**:显式点选的表 = 限定(点了就用这几张);
   选中的图谱 = 锚定本体源,**在其中按问句打分召回**,不再全量倾倒。
3. **`_join_hints` 形状无关**:两种 IR 结构都能读;键优先取结构化 `evidence`,
   缺失时从 `note` 解析并把来源标为 `note`。
4. **构建器落结构化 JOIN 键**(两条构建路径都补)。
5. **键名词根校验**:子键与父键词根不一致时,不把该键对当 JOIN 依据下发。
6. **锚定链路可视化**:本体规模 → 问句命中 → 关系扩展 → 入上下文 → SQL 实际用,
   并给出**命中证据**(是哪个词把这个对象钓出来的)。

## 一个被顺带挖出来的假关系机制

给自建本体做出 JOIN 键之后,键对肉眼可见地不对:

```
dim_product.prod_id      = fact_production_order.order_id     [已验证]
dim_equipment.equipment_id = fact_downtime.downtime_id        [已验证]
```

查数据坐实了原因:**两侧都是从 1 开始的稠密自增代理键**,
`dim_product.prod_id` = {1..15}、`fact_production_order.order_id` = {1..N},
值域天然 100% 重合,再叠加"父键唯一"就被判成 `verified`。
真关系长的是另一个样子:`fact_sales_order.order_id → fact_delivery.order_id`
重叠 90%、值从 126 起。

`built_9c3fd1` 的 12 条带键关系里 **10 条**是这么来的;示例本体 60 条里也查出 1 条
(`fact_material_consumption.material_id → dim_product.prod_id`,而库里明明另有 `dim_material`)。

**键名词根**是廉价而有力的证伪信号:真外键两端要么同名(`order_id=order_id`),
要么是缩写(`emp_id↔employee_id`);假关系两端是不同实体的 id
(`prod_id↔order_id`、`line_id↔equipment_id`)。
该规则在 72 条带键关系上降级了 11 条,逐条查证均为值域巧合;
被放行的 61 条未逐条核验,只抽查了若干条真关系(如 `order_id→fact_delivery.order_id`
重叠 90%、值从 126 起)——**校验拦的是明显假的,不保证放行的都真**。

## 为什么这样做 / Rationale

- **「选了本体」必须意味着「按这套本体作答」**,否则选择框是装饰。
  这也是本体作为语义罗盘的底线——罗盘不能永远指向同一个方向。
- **选表与选本体是两件事**。点了 3 张表就该只用这 3 张(用户已经替系统做了判断);
  选了一套本体是圈定语义范围,范围内仍需按问句锚定。此前两者被塞进同一个
  `focus_tables` 通道,才有了"选图谱 = 倾倒全部表"。
- **错键比无键更糟**。无键时引擎按列名推断,还有口径校验兜底;
  错键被当成"本体已验证的 JOIN 依据"下发,校验反而会放行它。
  所以存疑键**降级为「关联(键见列名)」而不是照发**。
- **只降键,不删关系**。语义关系(设备 经历 停机)可能是对的,错的只是物理键;
  删掉会丢掉建模成果,判断权在人。
- **构建器改为送审而非直接判 verified**。反造假规范说 verified = 数据裁定,
  而值域重合根本不构成裁定证据——这是**收紧裁定条件**,不是绕过规范。
- **回退要出声**。选中的本体若无绑表对象(如应用本体 149 个概念全无绑表),
  生不出 SQL,此时回退示例本体并在 UI 明说,不静默换本体。

## 影响 / Consequences

- 选中图谱后锚定本体随之切换,实测三套本体各自锚定:
  demo 108/60 → 召回 14 · `built_9c3fd1` 19/16 → 召回 12 · `cq` 5/5 → 召回 4。
- 构建产物第一次能给出 JOIN 提示(此前恒为 0 条)。
- 问数缓存键纳入锚定本体——**换本体却复用旧答案等于拿另一套本体的结论**。
- 对话框内可见完整锚定链路与命中证据:
  `19 本体对象 → 8 问句命中 → 4 沿关系扩展 → 12 入上下文 → 2 SQL 实际用`。

## 代价与边界 / Trade-offs

- **键名校验会误伤命名不规范的真外键**(如 `mat_id → material_code`,词根 mat/material
  长度 3 恰好放行,但 `m_id → material_id` 会被拦)。误伤方向是安全的:降级成
  "键见列名",引擎仍可按列名推断,不会因此产生错误 JOIN。示例本体 60 条中仅 1 条
  被降级,且经查证那 1 条本就是假关系。
- **既有构建产物的键靠解析 `note` 回填**,UI 标为「键·备注回填」。
  复合键的父列名不在 note 里,回填不了,这类关系降级为无键。
- **多选图谱按主键去重合并**,不同本体里同名对象会被当成同一个。
  跨本体对齐(同一实体在两套本体里叫不同名)不在本轮范围内。
- 口径校验的表白名单仍包含**数据目录全表**,所以选了小本体也不会因为表不在本体里
  而被拦。收窄它是另一个口径决策,本轮只让 JOIN 键校验跟着锚定本体走。

## 补做:让锚定「看得见」,而不只是「存在」

上一版把锚定画进了对话气泡,反馈仍是「没有可视化出来」。按用户视角复现才发现原因:
**答案出来后对话流自动滚到底,锚定区块被顶到视口上方**——实测其 `top = -380px`,
用户只看到图表和数据概览。功能在,但看不见等于没有。

两处补救:

1. **常驻锚定条**(`#dq_ancbar`,固定在对话区顶部,不随对话流滚动):
   一行显示 `本体锚定 <本体名> · 19 本体对象 → 8 问句命中 → 4 沿关系扩展
   → 12 入上下文 → 2 SQL 实际用`,可展开子图与证据。
   与气泡内的区块**共用同一段渲染**(`dqAnchorHTML(a, bare)`),不做第二份实现。
2. **「在图谱中高亮这一块」**:切到本体图谱页,把本次锚定到的对象着色、
   其余淡出,SQL 真正用到的加粗边框,并给出
   「本次问数锚定到该本体的 12/19 个对象」的说明与一键清除。
   这才正面回答了「选了本体的**哪一块**」——子图孤立地画,看不出它在整套本体里的位置。

一处实现坑:高亮说明最初写进 `#g_info`,被完备度查询的异步回调整体覆写了
(`$('#g_info').innerHTML = ...`),表现为提示一闪即没。改用独立的 `#g_hlbar`。

教训:**"渲染出来了"不等于"用户看得见"**。带自动滚动的界面里,新增内容要么
钉在视口里,要么就等于没做——验收得按用户视角截整页,不能只截自己关心的那个元素。

## 又一次测试脆性(与 DR-032 那次同源)

DR-032 里我把 UI 实操的等待条件从「文本长度兜底」改成了严格匹配「执行查询」。
这轮它以 420 秒超时的形式爆出来——看着像功能坏了,实际是:
**问数命中缓存时秒回,`done` 直接渲染,而执行记录 `<details>` 在有结果时是折叠的,
`innerText` 读不到隐藏内容**,于是「执行查询」永远不出现。

两次的病根是同一个:**拿页面文本当完成信号**。文本会因为加内容、折叠、缓存路径而变。
这次改用**状态信号**:卡片数增加 且 发送按钮复原(`ask()` 在 `finally` 里恢复它),
再在断言前显式展开 `details`。

教训:等待条件要盯**状态**(计数、禁用位),不要盯**渲染出来的字**。

## 点示例必须真跑

新对话里点示例问题(如「最近几个月毛利率的变化趋势」)会秒回——命中的是问数缓存。
反馈指出:**缓存的记录属于「历史对话」的语义,不该在点示例时给出**。

示例是给人看「这套系统怎么工作」的入口,秒回一个早算好的答案,
看上去像预置好的演示,而不是真的在问数。改为示例点击强制 `nocache`
(`dqAskEg` → `ask(true)` → 请求体带 `nocache`)。

**只改示例这一条路径**:手动输入同一问题仍走缓存并标「缓存·秒回」——
那是用户主动重复提问,秒回是收益不是欺骗。实测示例两次点击各 127s / 137s
且无缓存标记,手动重复提问 0.5s 命中缓存。

即时问数走 `/api/metric/quick`(确定性 SQL,无 LLM 缓存),不受影响。

## 对话框里不出现缓存答案

先只让「点示例」强制重跑,手动输入仍走缓存——理由是「用户主动重复提问,秒回是收益」。
反馈随即指出:手输「这一个月的毛利率变化趋势」弹出来的也是历史记录。
复现确认:该问句此前被问过,`_QA_CACHE` 按问题原文命中,0.5 秒返回。

这里我判断错了。**秒回的旧答案与「历史对话」里的记录,在界面上无法区分**——
用户看到的都是「一句话下去,立刻出现一份完整报告」,那看起来就是在放录像,
而不是在问数。区分它们的只有一个 `缓存·秒回` 小标签,而这恰恰是在要求用户
替系统解释自己。

改为**对话框里的每一次提问都真跑**(`nocache:1`),点示例与手动输入一致。
要看以前的答案,去左侧「历史对话」——那是记录该待的地方,语义清楚。

代价:重复提问也要等约两分钟(GLM 实测 101–132s)。这个代价是值得的——
一套用来展示「本体如何驱动问数」的系统,可信度比响应速度重要;
何况执行记录与锚定链路是逐步流出的,不是空白等待。

缓存机制本身保留(`/api/chat` 等非交互消费者仍可用),只是交互路径不再读它。

## 一个由本决定引入的崩溃(demo 打通时发现)

`build_context` 里长期写着 `o.get("table", "")`。**默认值只在键缺失时生效**——
键在而值为 `null` 时返回 `None`,拼字符串即 `TypeError`。

锚定源恒为 demo 时永远不会犯:demo 的 108 个对象每个都有 `table`。
DR-033 让**任意图谱都能当锚定源**之后,`built_bd2fec` 这类
「10 个对象里 9 个 `table: null`」的概念本体一被选中,问数就 500。

同类写法共 6 处,一并改成 `(o.get("table") or "")`。

顺带修了第二个问题:**混合本体**(部分对象绑表、部分是纯概念)里,
无绑表对象会挤占召回名额,极端情况下上下文一张表都没有。
挑表时先滤掉无绑表对象,由既有的回退校验兜底。

回归断言 AO40 遍历仓内**全部图谱**逐个作锚定源,任一崩溃即失败——
这类边界靠举例测不出来,得穷举。

## 界面版本自检(为什么「改了却没生效」)

点示例强制重跑上线后,反馈仍是「还是缓存好的例子」。照描述逐环复现,结论是
**代码没问题,页面是旧的**:请求体确实带 `nocache:1`、耗时 132s 真跑、无缓存标记、
历史对话新增一条。标签页开着不刷新,内存里的 JS 就还是改动前那份。

`Cache-Control: no-cache` 只能保证刷新时拿到新文件,救不了一个一直开着的页面。
于是加了 `GET /api/uiver`(返回 `ui/index.html` 的 mtime),页面加载时记下版本,
之后每 60 秒自检一次;发现服务端文件变了就弹一条可关闭的提示:
「界面已更新,当前页面还是旧版 —— 刷新以生效」。

两个实现要点:
- 横幅**挂在 body 上**而非某个 `.page` 容器内。首版放进了 `#p_chat`,
  结果 `display:block` 也看不见——外层页面容器本身是隐藏的。
- **首次加载只记版本不打扰**,只有检测到变化才提示。

教训:这类系统我们改得频繁,而对方的页面可能开了几个小时。
**「我改了」与「你看到的」之间隔着一次刷新**,系统应该自己说出来,
而不是靠人反复反馈同一个问题。

## 上手路径打通时补的四处(2026-08-04)

写《快速入门》时按「只 clone 本仓 + 一个 API Key」的视角从零走一遍,发现这条路走不通。
四处断链的共同点是**静默失败**:现象与原因隔得很远,配置者无从判断哪里出了问题。

| 断链 | 现象 | 根因 |
|---|---|---|
| 垫片不承载 driver 注册 | 配了 Key,`runtimes` 仍为空 | `openai_runtime.register()` 只写在「引擎导入成功」分支内 |
| 规划调用写死 60 秒超时 | `llm_plan` 显示「返回 42 字符」后回退模板 | 推理型模型规划实测 61~79 秒,每次刚好越界 |
| `tables[]` 未归一 | 选中自建本体,锚定条却显示内置本体 | `quick_build` 产出用 `tables[]`,读取端只认 `table` |
| 本体缺 `attrs` | SQL 报 `no such column` | 上下文形如「表 X(): 」,无列名可依,模型只能猜 |

第一处此前一直没暴露,是因为 `PLATFORM` 的默认值指向同级 `ontology-engine` 目录——
开发机上该目录存在,**「独立运行」这一档从未被真正验证过**。

第三处的影响超出预期:`app` 本体 82/149 个对象、另一套构建产物 108/108 个对象
此前都被判为「无绑表」而静默回退。修复等于解锁了两套本体。
相应地,两条依赖「某图谱是纯概念本体」的回归断言前提已不成立,改用合成图谱验证回退。

## 边界收敛

- `_table_cols()` 只缓存成功结果:数据底座临时不可用时若把空列表写入缓存,
  恢复后仍会一直返回空。
- 表名经标识符白名单校验后才拼入 `PRAGMA`,与全站标识符消毒口径一致。
- `_obj_table()` 跳过 `tables[]` 中的空值;`attrs` 的中文名为 `None` 时不渲染字面量
  `"None"`——那会被原样喂给模型。
- 垫片的 `get_runtime()` 点名未注册的驱动时如实报错,不以另一驱动顶替。
- `_drv_order()` 补入 `openclaw`:它出现在运行时列表却不在尝试顺序中,
  设置后会被完全忽略,表现为「切了引擎没反应」。
