# DR-075 · 200 表合成验证库生成器 v2:业务链派生、如实登记底库缺陷与生成后语义校验

- **状态 / Status**: accepted
- **日期 / Date**: 2026-10-03
- **关联 / Refs**: [[DR-074-contract-200-synthetic-db-evaluation]];
  实证=`tests/unit/test_contract_200_generator.py`

## 上下文 / Context

对 v1 生成的库做了独立审计(只读,脚本按业务规则逐项查):结构层面没有问题(200 表、声明外键零违例、单行公式成立),
但业务上大面积讲不通:

- **跨表关系互相矛盾**:新表的引用按行号公式逐列独立取值,发运明细的产品与其订单明细不同(100%)、
  投诉客户不是被投诉订单的客户(98%)、检验批与报废的产品不是工单产品(91%)、传感器不在所属设备上(99%)、
  任职部门不是员工所在部门(93%);单据头金额与明细合计全部不等,调拨单与供应商合同 140 张表头里 120 张没有明细。
- **取值是模板**:614 列是「表名:列名:0001」占位串;所有事实表第 n 行的数量、单价、金额完全相同;
  计量单位与币种按行号轮转(考勤以千瓦时、人民币计),汇率恒为 1;币种表带 51% 的「税率」,
  三个班次分属三个工厂,项目计划结束早于开始。
- **底库缺陷被掩盖**:物料消耗 82% 引用不存在的工单,v1 把它们轮流挂到现有工单上;子单据日期被改成父单据日期;
  汇总层重复粒度被删除。
- **元数据与验证案例失真**:字段中文名多半是未翻译的英文词元,`line` 一律译成「明细」(产线 ID 成了「明细标识」);
  验证案例 COMPOSITE_KEY 声称「发运单号 + 行号」唯一,数据里 220 张发运单全部重复;验证结果表是模板行。

## 决定 / Decision

生成器升到 v2(`scripts/build_contract_200_db.py` + `contract_200_semantics` / `contract_200_values` /
`contract_200_metadata` / `contract_200_checks`,均只用标准库):

1. **引用沿业务链派生**:明细继承表头(发运明细取其交付对应订单的订单明细与产品;到货预告明细取预告采购订单的订单行与物料);
   检验批、报废、工序、在制品的产品与产线取自工单;工序取自工单产品的工艺路线;工艺参数记录的设备在工单产线上、
   参数适用于设备类型;告警与监测的设备取自传感器;备件适用于设备类型;合同、索赔、质量问题的物料由该供应商供应;
   库位所在仓库、员工所在部门与部门下的岗位、产线所在车间的班次。其余引用按偏态分布抽取(少数父记录被频繁引用),不再轮转。
2. **表头由明细汇总**:每张表头至少一条明细,行号在表头内连续唯一;表头数量、金额由明细合计,单价为加权均价;
   销售订单明细两行恰好拆分原表订单的数量与金额;总账凭证每张两行借贷同额;税票明细拆分发票不含税金额。
3. **每张表只保留合乎含义的列**:事实表列分为单据核心、数量组、金额组、时长、比率评分与业务属性组,按表配置
   (考勤没有金额与币种,工艺参数记录没有良率);计量单位按表的含义固定,币种以人民币为主、外币按汇率折本位币;
   维表按自身含义配置属性(币种有符号与汇率,不再有税率;每个车间三个班次,起止时间为真实钟点)。
   所有属性列都有按记录上下文生成的取值,没有占位串;度量按表独立抽取,不在表间重复。
4. **底库缺陷如实保留并登记**:不再修补孤儿引用、改日期、删重复粒度;逐项写成验证案例(检测 SQL + 生成时实测数量),
   并在数据质量问题表里列为未关闭问题。声明外键的违例只允许是登记的四类底库孤儿,数量须一致。
5. **刻意构造并登记的脏数据**:叶子事实表约 2% 逻辑删除、部分维表记录停用、遗留领料约 5% 物料编码在主数据中找不到。
6. **元数据按含义生成**:引用列命名为「角色 + 父表中文名 + ID」,其余列整词翻译,缺译即报错;每张新表有各自的说明(粒度与关联)。
7. **验证案例可执行**:每个案例带检测 SQL;断言性质的挑战案例(复合键唯一、金额 = 数量 × 单价、表头 = 明细合计等)
   违反数必须为 0,否则生成失败;验证结果表记录每个案例的实际执行结果。
8. **生成后语义校验**(`contract_200_checks.run`,85 项):跨实体一致性 23 项、表头与明细、行号、占位串、
   非设计恒定列、表间重复度量、机械轮转引用、单位与汇率、业务公式、日期先后、元数据翻译、验证案例自述与结果;
   任何一项不通过即不发布。也可单独运行:`python3 scripts/contract_200_checks.py <库>`。

## 后果 / Consequences

| 项目 | v1 | v2 |
|---|---|---|
| 表 / 列 / 行 | 200 / 5,598 / 209,451 | 200 / 5,038 / 209,343 |
| 跨实体一致性(23 项) | 多数 81%~100% 不一致 | 全部 0 |
| 表头 = 明细合计 | 全部不等 | 全部相等 |
| 占位串列 | 614 | 0 |
| 新表恒定列 | 23% | 16%(均为设计恒定:单租户、每表固定单位/币种/移动类型等,校验器内列明) |
| 声明外键违例 | 0(孤儿被挂到现有记录上) | 7,841,全部是登记的四类底库孤儿 |
| 验证案例 | 12 条模板,1 条与数据矛盾 | 30 条可执行:挑战 12、刻意脏数据 3、底库缺陷 15 |

- 列数从 5,598 降到 5,038:去掉了不适用的模板列,仍满足合同不少于 5,000 列;声明外键从 476 降到 418,
  因为不再给没有金额、数量的表声明币种与单位外键。
- 同一种子重复生成,库文件 SHA256 一致。
- 底库的四类时间倒序(交付早于订单等)在 v1 只出现在被挂接的孤儿行上;不再挂接后实测为 0,不登记。

## 备选与不做 / Alternatives

- **继续修补底库缺陷**:不做。修补让关联看起来成立,评测会把编造的关联当成事实;如实保留并登记,
  评测智能体是否识别孤儿与不一致才有意义。
- **为凑足列数保留不适用的模板列**:不做。改为给常用属性组补充有含义的列(运费、经办人、检验员、摘要),列数仍过 5,000。
