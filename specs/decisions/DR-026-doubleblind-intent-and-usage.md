# DR-026 · 双盲意图检测与本体使用度回流

- **状态 / Status**: accepted
- **日期 / Date**: 2026-08-02
- **关联 / Refs**: [[DR-019-deepqa-upgrade]](口径校验)、[[DR-024-competency-questions-driven-build]](锚定策略)、[[DR-025-drift-and-penetration-chain]]

## 背景 / Context

《本体智能研究报告(1.0)》(AIIA × CCSA TC601)两处要点,本仓此前均为空白:

**其一,电力配电网案例**:"将复杂分析标准化为『获取对象→提取数据→计算指标』三步流程,
并**配套双盲检测机制确保查询意图准确性**"。

我们的问数链路是单通道:`问句 → LLM 生成 SQL → 口径校验 → 执行`。
口径校验(DR-019)管的是「SQL 合不合规」——表在不在白名单、JOIN 键落不落本体关系;
它管不了「**SQL 答的是不是用户问的那件事**」。一条完全合规的 SQL 可以查一张
完全不相干的表:校验放行,用户拿到一个数字合理、口径清晰、但答错了问题的答案。
这正是排障表里的第一类症状「答非所问」,而我们此前没有任何机制拦它。

**其二,阶段六**:"定期评估本体的**业务调用频次**与决策支撑效果,以使用数据驱动
优化迭代,形成『建设—应用—反馈—优化』的闭环"。扫描确认本仓 0 命中。

## 决定 / Decision

1. **双盲意图检测** `intent_check.py`,接入问数两条分支(同步 + SSE),
   位置在口径校验之后、执行之前,产出 `intent_crosscheck` 步骤。
   两条**互不透传**的通道各自判定意图后才比对:

   | 通道 | 输入 | 产出 |
   |---|---|---|
   | A 声明意图 | **只看问句** | 锚定的本体对象 + 命中的指标词 |
   | B 实际意图 | **只看 SQL** | 反解 FROM/JOIN 的表 → 映射回对象 |

   四态:`aligned` / `partial`(漏维度) / `mismatch`(完全不相交,疑似答非所问) /
   `unknown`(问句无锚点,不做判断)。

2. **使用度回流** `usage_stat.py` + `GET /api/ont/usage/<key>`。
   埋点复用双盲已反解出的对象(零额外解析开销),把调用频次与证据状态交叉,
   直接产出建模优先级。

## 为什么这样做 / Rationale

- **两条通道都不调 LLM**。用模型验模型是同源偏差——生成 SQL 时理解错的意图,
  校验时多半还是同样理解错,"看起来对"会被判成"对"。确定性反解虽然覆盖面窄,
  但每个结论可回放、可解释,与本系统一贯的认识论一致。
- **只观测,不阻断**。确定性反解必然有漏判(如 SQL 走视图名、口径卡走派生表),
  若因误判挡住正确答案,代价远高于在执行记录里标注一句存疑。判定结果进 steps 供人看,
  不改变执行流。
- **`unknown` 不冒充通过**。问句锚不到任何对象时(如"产量的月度趋势"这类纯口径提问),
  诚实返回"无从比对"而不是默认放行——把"没检查"说成"检查通过"是最坏的一种谎。
- **埋点是只读旁路**。记录失败一律静默吞掉,绝不因统计影响问数;落盘用原子替换
  (写 tmp 再 os.replace),避免读到半截文件;不记录问句原文,只记对象键与计数,
  避免把业务问句沉淀成需要脱敏的资产。

## 影响 / Consequences

- 问数执行记录新增 `intent_crosscheck` 步骤,用户可见「这条 SQL 答的是不是我问的」。
- 使用度报告给出可执行的建模优先级:
  **高频 × 有候选关系** → 优先补裁决(业务天天在用,证据却不足);
  **零调用** → 疑似建模过度(须先确认统计窗口够长)。
- 与 DR-024/025 合为四问:够不够用 · 通不通 · 对不对得上数据 · **答的是不是问的**。

## 代价与边界 / Trade-offs

- 意图锚定依赖**对象名在问句中完整出现**。业务口径提问(如"产量的月度趋势")
  锚不到以表名中文命名的对象,只能判 `unknown`。这暴露了一个更深的问题:
  **本体对象缺业务别名**——真正的解法是给对象补别名,而非放宽匹配(放宽会制造假阳性)。
  已知边界,如实标注。
- 反解只覆盖 `FROM/JOIN` 的直接表名;通过视图、CTE 间接引用真实表的情况会漏判。
  CTE 已显式排除(把 CTE 当表会让"SQL 查了什么"失真),视图暂不追溯。
- 统计**自埋点起累计**,历史调用无法回补;零调用率在统计窗口早期必然虚高,
  报告里已写明"须结合窗口长度判断,窗口过短时不应据此裁剪"。

## 实测佐证

接入后用真实问句验证,抓到一例**真阳性**:用户问"业务员维度表里有多少人",
模型生成的 SQL 却去查销售订单表做去重计数——SQL 标题自己都写着"非维度表口径"。
数字看着合理,答的却是另一件事;口径校验全程放行,双盲判定 `mismatch`。
这正是引入该机制的原因。
