# DR-034 · 中文召回改反向匹配;算子按中文名定位

- **状态 / Status**: accepted
- **日期 / Date**: 2026-08-04
- **关联 / Refs**: [[DR-027-business-alias]](业务别名)、[[DR-033-selected-ontology-as-anchor]](锚定源)、[[DR-026-double-blind-intent]](双盲意图)

## 背景 / Context

按《教程:接大模型 → 会话式建本体 → 基于本体问数》逐步实操,连续暴露四处问题。
四处都不报错、都能出答案,只在「答得准不准」「说得对不对」上失真。

### 一、中文别名从来没生效过

DR-027 立了业务别名,理由是「业务用语与表名中文往往不同」。代码把别名并进了评分语料,
`test_all` 也有断言。但实测:给「生产日度汇总」加别名「产能」,再问
「车间近期产能怎么样」,该对象的命中证据仍是空的。

根因在匹配方向。问句按标点与空格切词:

```
"车间近期产能怎么样"  →  ["车间近期产能怎么样"]      # 整句一个词元
"车间 产能 趋势"      →  ["车间", "产能", "趋势"]     # 加了空格才切得开
```

随后拿这些词去对象语料里找(`w in txt`)。中文长句切不开,自然一个都匹配不上——
**中文召回一直只靠术语词典把问句折成英文词**(`workshop`、`capacity`),
凡是词典里没有的中文业务词,补进本体也是白补。指标召回同一条路径,同样失效:
「本月计划产量是多少」召不回名为「计划产量」的指标,只有整句恰好等于指标名才行。

### 二、算子只认英文主键,对话式改本体走不通

助手按人的说法回提议 `{"op":"set_alias","target":"obj:销售订单"}`,而对象主键是
`SalesOrder`,`/api/ont/apply` 报「对象不存在」。**照着助手的提议点确认必然失败**,
凡是 `cn ≠ name` 的本体(会话式构建产出的都是)全中招。

### 三、离线白名单漏放六个本地算子

`apply_any` 自己实现了 9 个算子,与上游引擎无关;但引擎缺失时的放行白名单只列了
3 个。改动词、改基数、增删关系明明不用引擎,却被 503 挡回「编辑引擎未就绪」。

### 四、三处「说得不对」

- 执行记录首步写死「加载 **示例** 本体上下文」,选了自建本体也照喊示例,
  与下一步 `anchor_ontology` 自相矛盾。
- 铸造产物 `FORGED_DIR` 落在上游引擎目录下,独立运行时 `/api/ont/forge` 以 500
  裸栈失败——而独立运行是本仓的默认形态。
- `/api/db/check` 用 `sqlite3.connect` 直连,**库缺失时静默新建空库**,
  此后只读连接都能打开却查不到表,把「库没了」伪装成「库是空的」。
  `ro_connect` 的注释写着「不静默新建空库,防丢库被掩盖」,健康检查自己绕过了它。

## 决定 / Decision

1. **中文走反向匹配**:拿本体自己的中文词汇(对象中文名、业务别名、属性中文名、
   指标名)当词典,到问句里去查(`term in question`)。不引入分词器——分词器带词表、
   带版本、带歧义,而反向匹配确定、可回放、零依赖。单字不参与:「的」「和」满篇皆是。
   英文仍走原有正向匹配(≤2 字缩写只认整词,DR-027 已定)。
2. **对象定位按主键 → 中文名 → 表名 → 业务别名依次降级**。主键优先,避免中文重名时
   抢掉精确命中。关系端点与级联删除统一走同一套规范化,否则「按中文名删对象」会删掉
   对象却留下悬空关系。
3. **离线白名单与 `apply_any` 的实际分支对齐**,并用 AST 对账钉死(QS11)。
4. **据实回显**:本体名从锚定结果取;`FORGED_DIR` 装了引擎写引擎目录、否则写
   `workdir/`,读取并两处;`/api/db/check` 改走 `ro_connect`。
5. **「意图一致」写明比对基数**:通道 A 只锚得到本体里有的词,问句里「停机时长」
   之于本体「停机记录」本就不参与比对。结论改为「SQL 覆盖了问句锚定到的 N 个业务
   对象(…)」,让这句话的边界可见,不被读成「问句问的都答了」。

### 五、技能与工具面的三处不一致(逐条核对技能时发现)

- **智能体列表永远列不出技能包**。它硬编码同级「上游本体引擎」目录,该目录早已更名,
  且不受 `DATAMIND_ENGINE_DIR` 控制;同一批技能在构建页(`/api/build/skills`,走
  `PLATFORM`)却列得出来 —— 两处对"装了哪些技能"给出相反结论。
- **`/api/ont/rebuild` 无确认闸**。它丢弃整个草案层(全部人审与编辑),而 `undo` 只退
  一步、退不回来。上游引擎的同名端点一直要求 `confirm:true`,`auto-ontology` 技能也
  照此写明「不带 confirm 服务端会拒绝」—— 照技能行事的 agent 会在这里踩空,而该端点
  界面上并无入口,只对 agent/脚本开放,连人工二次确认都没有。
- **`/api/ont/skills/write` 会凭空造引擎目录树**。它无条件 `makedirs` 到 `PLATFORM`:
  父目录可写时造出一棵空壳(随后被当成"已装引擎"),只读位置则 500 裸栈。
  与 `/api/db/check` 静默建空库是同一类错误 —— 缺失的东西被就地伪造出来。

## 决定 / Decision(续)

6. **技能目录一律走 `PLATFORM`**,不写死目录名。
7. **`rebuild` 必须显式 `confirm`,且不直接删** —— 编辑日志改名留底(`.discarded`),
   误触可恢复;响应回报丢弃了几条。
8. **`skills/write` 按引擎在否分流**:装了引擎写引擎技能库,否则写自己的
   `workdir/custom_skills`(写入即可被构建页选用),两种情形都不再伪造目录。

## 代价 / Consequences

- 反向匹配是 O(词数 × 对象数) 的子串查找,对象上千时仍是毫秒级,可接受。
- **召回面变宽**:此前中文命不中就回落「默认候选」,现在会真命中,进上下文的表可能
  变化,已有问数的 SQL 未必逐字复现。判据与门禁不变,答案口径不受影响。
- 反向匹配只认「本体里有的词」。问句用了本体没有的说法(如派生口径「毛利率」)仍命不中——
  这是本体该补的内容,不是召回该猜的东西。文档据实写明,不粉饰。
- 中文名重名时,主键优先的降级顺序可能让人意外;此时报错优于猜错,由使用者改用主键指代。
- `rebuild` 加闸后,原先不带 `confirm` 的调用方(含回归自身一处)会收到 400。这是有意的:
  破坏性动作宁可打断调用方,也不该默默执行。`.discarded` 留底文件不自动清理,由使用者删。
