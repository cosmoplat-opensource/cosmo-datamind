## 上下文 / Context

用 DR-076 重建的两个库(108 表基础库、200 表验证库)做了一次端到端评估:构建体检给出分轮计划,
按计划逐轮构建(与界面「按计划逐轮构建」相同的请求,接入真实大模型),再按固定问题问数,
与独立编写的 SQL 结果比对。发现三类与库无关的通用问题。

1. **库内数据字典没有用上**。构建取证与构建体检只读只读抽样生成的 `_dm_tables` / `_dm_columns`。
   两个演示库的表、字段注释在库内的 `dim_table_metadata` / `dim_column_metadata` 里,
   DR-074 起作为连接证据的「外键,关联 dim_x」注释在构建中实际没有读到。
2. **同名键挂错父表**。`line_id` 既是产线表主键,也是采购订单行表主键;`order_id` 既是销售订单主键,
   也是生产工单主键。两张父表的整数区间都覆盖子列取值,键名对两边一样相符,于是两条都判为已验证;
   正确的一条反而因「键名证据不唯一」被验收检查列为阻断问题(108 表 13 条)。
   另有子表自己的主键(`fact_payment_out.payment_id`)被连到同名主键的另一张表。
   这些列的字段注释都写明了指向哪张表,或写明是本表主键。
3. **问数猜筛选值**。问数模型只看到列名(每张表最多 18 列),不知道枚举列的实际取值,
   写出 `status='完工'`(实为「已完成」)、`warehouse_type='成品仓'`(实为 `finished`)、`status='ABSENT'`
   (缺勤记在 `attendance_result`)这类条件,查询返回 0 行。宽表的相关列也常被 18 列上限截掉。
4. **问数上下文漏掉码表、答非所问误判**(修正 1~3 后重跑问数时发现):
   - 命中表的一跳邻居按关系列表先后取 4 张,设备主表的车间、资产等邻居先占满名额,
     停机记录 `reason_code`(取值 1~8)指向的停机原因表进不来,模型写出 `reason_code = 6`(实为「能源中断」);
   - 「安全事件」与表中文名「事故」字面不同,术语词典虽能把它对应到 `fact_incident`,但只记 1 分,
     低于只命中「事件」「event」的报废事件、排放事件等表;
   - 「设备故障导致的停机总时长」中的「设备」被意图核对当成问句对象,按 `reason_name = '设备故障'` 过滤、
     未 JOIN 设备表的总量查询被判为答非所问而丢弃,只剩按设备拆分的结果。

## 决定 / Decision

1. **读取库内数据字典**(`build_prep._comments`):没有 `_dm_*` 时,读 `dim_table_metadata`(表名、中文名、说明)
   与 `dim_column_metadata`(表名、字段名、中文名、说明),中文名与说明合成一条注释。构建体检、构建取证
   (`server._gather_evidence`)与交叉复核共用同一来源。
2. **注释写法的识别**(`code_contracts.comment_contracts`):
   - 「引用产线(dim_production_line.line_id)」这类先写中文名、括号里写表名的写法也能识别;
   - 「表.列」写法取表名为父表、列名为父列(此前把列名当表名,找不到父表)。
3. **交叉复核增加字段注释通道**(`ontology-cross-check` 技能):
   - 注释写明「外键,关联 X」时,连到 X 为支持证据,连到别的表为强冲突;
   - 注释写明是本表主键且没有写外键时,把它当外键连到别的表为强冲突;
   - 强冲突照原规则把已验证关系降为候选并写明原因,不删除关系。
4. **问数列说明**(`server._obj_cols_text`):
   - 问题提到的列(中文名的任一双字片段、或英文列名中长度不少于 3 的词出现在问题里)排在前面,不被列数上限截掉;
     列数上限由 18 提高到 30;
   - 不同取值不超过 10 个的文本或整数列,附上库中的实际取值(如 `status(状态;取值:已完成/待生产/生产中)`);
     键、编号、日期时间列不附。
5. **问数上下文的表召回**(`server.build_context`):
   - 一跳邻居先全部收集再取前 4 张,依次按:命中表经编码列(不同取值不超过 10 个)引用的码表、
     邻居自身与问句的相关度、所连命中表的排名;
   - 术语词典把问句用语直接对应到某张表时,该表加 12 分,与问句原样出现完整中文名同等;
   - 列排序时,问句说出了某列的实际取值(「缺勤」之于出勤结果)也算提到该列。
   - 术语词典补「fact_incident → 安全事件」「fact_incident_inv → 安全事件调查」:
     表中含未遂事件(near miss),译作「事故」不准确。
6. **意图核对**(`intent_check.cross_check`):问句中被 SQL 原样用作筛选值的词先去掉,再锚定问句对象;
   只用 SQL 的字符串常量,不看 SQL 查了哪些表。问句另外单独提到该对象时照常比对。
7. **问数计划提示**:第一个分析直接回答问题本身(问总量给总量),拆分与趋势放在其后。
8. **界面**:
   - 构建页技能卡的说明限制为 3 行,完整内容在悬停提示与「查看/编辑」中显示
     (技能增加到 5 个后,首张卡高度超过 160 px,UI 走查失败);
   - 界面最小字号统一为 11 px(原有 10 px、10.5 px、10.8 px 的提示与标签);
   - 界面文案中夹在中文之间的半角逗号、分号、冒号改为全角;
   - 四个领域与方法技能的说明改用全角标点,「迁移空壳」统一改称「迁移遗留空表」。
   - 本体图谱(`ui/modules/graph-render.js`,由 `index.html` 拆出,主文件保持 2500 行以内):
     节点框宽随名称长度(132~240 px),长名称不再溢出框外;节点超过 40 个时连线标签默认隐藏、悬停显示;
     分层布局中没有关系的对象不参与分层,布局后按网格排在连通部分下方(此前 50 个孤立对象叠成一列,
     全图被拉成细长条);初始视图聚焦不用动画(动画被第二次自适应打断时,视图停在空白处);
     底部操作提示加白底,不与节点、连线重叠;布局选项「分层(原版)」改为「分层」。
9. **示例本体与术语词典的译名**:与库内数据字典对照,改正示例本体中的误译:
   `dim_bom_line`「BOM产线」→「BOM行」、`fact_po_line`「采购订单产线」→「采购订单行」(line 指单据行)、
   `dim_operation`「操作」→「工序」、`dim_hazard`「隐患」→「危险源」(hazard 在职业健康安全管理中译作危险源)、
   `DWS_FINANCE_DAILY`「财务日汇总」→「财务月汇总」(表中只有 18 个月末日期)、
   `DWS_IN_SALES_DAILY`「内销日汇总」→「售中日汇总」、`DWS_CASH_DAILY`「现金日汇总」→「变现日汇总」、
   `DWS_AFTER_SALES_DAILY`「售后销售日汇总」→「售后日汇总」、`fact_incident`「事件」→「安全事件」,
   名称中的「按人x月」改为「按人×月」;术语词典同步补充表级与短语级译名,词元 hazard 改译「危险源」。

## 后果 / Consequences

评估方法:按构建体检的分轮计划逐轮构建(接入真实大模型),参考关系 = 声明外键 + 字段注释写明的引用;
问数按固定问题集(108 表 12 题、200 表 16 题)调用 `/api/chat`,与独立编写的 SQL 结果比对。
评估脚本、问题集与报告在本次评估的临时目录中,未入库。

| 项目 | 修改前 | 修改后 |
|---|---|---|
| 108 表:关系召回 / 精确率 | 89.8% / 88.5% | 100% / 98.5% |
| 200 表:关系召回 / 精确率 | 90.8% / 80.3% | 97.5% / 85.5% |
| 108 表验收阻断问题 | 13 | 0 |
| 108 表问数 | 8 / 12 | 9 / 12 |
| 200 表问数 | 8 / 16 | 15 / 16 |

- 200 表库中被计为「精确率损失」的关系里,有相当一部分是参考集未收录但业务上成立的连接
  (日期列 → 日历表、科目编码 → 科目表、库位编码 → 库位表、合同号 → 合同表等),精确率是下限。
- 108 表问数未答对的 3 题都属于统计口径不同,问句本身允许两种理解:
  「各车间完工工单的实际产量」按下单日期还是完工时间归年;「各产线平均 OEE」取生产日汇总还是设备运行记录;
  「每月完工的工单数」指生产工单还是维护工单。
- 200 表未答对的 1 题(「PA66-GF30 的平均成交单价」)几次运行结果不一:有时按产品表关联、
  取简单平均(与加权口径不同),有时误选物料表而无结果。
- 问数由大模型生成 SQL,同一问题多次运行结果会有出入,上表为单次运行结果。

## 备选与不做 / Alternatives

- **把 `dim_*_metadata` 当成取证专用表、不建对象**:不采用。它们在库中就是普通表,问数也可能用到;只是额外作为注释来源。
- **问数时自动重试 0 行结果**:暂不做。附实际取值从源头减少猜值,重试会让每次问数多一轮模型调用。
- **码表无条件全部带入上下文**:不采用。200 表库有几十张码表,全部带入会挤占命中表的列说明。
