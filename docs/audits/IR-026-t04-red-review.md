## 按用户操作解释

1. 构建仍是原 TBox＋ABox 流程。浏览器实际确认类别、关系和属性，再查看本体候选；没有“选择应用”，检查表为空，也没有自动适配请求。这项已通过。
2. 用户点击行为树按钮才诊断。HTTP 用真实默认注册器检查新候选；缺类别应定位 schema.missing_role，缺执行字段应定位 execution.missing_metadata，并提供证据和对应修复动作。检查只新增报告，不新增本体、源文件或运行，不调模型。
3. 三类修复各司其职。缺类别打开原设计且不直接修改；缺执行结构先准备适配记录，让用户核对角色，确认后另点提交；业务缺项返回原任务，不补造技能顺序。
4. 保存有版本边界。成功适配产生同资产的新候选，保留父版本、原实例映射和历史设计；旧 JSON／OWL 字节不改。重复／并发请求、工作头变化、输入篡改或版本写入失败都不能造成重复版本或半套工件。
5. 业务补全复用原有实现。真实 TaskService 逐步明确零件、工位、载具和槽位，选择类型／感知／放置配置，补参数并确认；每次保存都检查当前总 JSON 与同版本 OWL 同构，旧版本保持不变。
6. 验证生成结果。将感知阈值明确改为 0.91，调用原编译器与校验器，核对六项公开参数及其来源，并与相同输入／配置的旧任务路径比较 XML 节点顺序和属性，不要求空白字节一致。
7. 自包含和策略保持。分别在任务开始前、补全后移走临时根中的原双 XML，再测试准备、补全、再次生成、读历史。strict 缺适配依据继续阻塞；offline 维持原规则；显式合成证据只验证软件流程，结果仍“执行未验证”。原任务返回使用独立 CAS，不能覆盖用户稍后的修改。
