# 2026-09-07 实际部署与验收

部署地址：<http://127.0.0.1:8092>。此为本机持续运行的系统，使用现有 `.env`、`workdir` 和已配置模型端点。
Gunicorn 23.0.0，单 worker、8个 gthread 线程；当前数据底座为随仓108表 SQLite。
工作目录、数据源和模型配置沿用本机配置，源码改进已加载；未向远端推送或发布公网地址。

## 运维入口

```bash
./start.sh
./status.sh
.venv/bin/python scripts/service.py restart
./stop.sh
```

启动器按字面值读取 `.env`，不执行其中的 shell 表达式；出错不打印变量值。
只管理匹配自己 PID 文件的 Gunicorn，端口占用时明确失败，不按端口杀其他程序。
`.deploy/service.json` 保存运行源码摘要与健康状态；日志在 `.deploy/access.log` 和 `.deploy/error.log`。
部署前已将原 `workdir`、`.env` 和文件摘要备份到 `.deploy/backups/20260907-013040/`；该目录私有且被Git忽略。
此部署可在终端退出后继续运行，未安装开机自启或公网TLS代理。

## 验收方法

- `scripts/test_deployed_http.py`：真实监听端口上的协议、安全、SQL只读、静态资源和有限并发检查，不调用模型或变更业务对象。
- `tests/frontend/live-deployment.py`：真实浏览器，未拦截或模拟HTTP响应。创建唯一“验收_”前缀本体，验证构建、图谱、人审及撤销、问数、窄屏；保留产物供复核。
- `scripts/test_deployed_ontology.py`：重放上述真实产物的verified关系、CQ、质量和问数SQL；不再发起模型调用。
- 不在日常工作目录直接运行会改写通用种子/引擎配置的旧回归套件；旧套件仍在隔离副本中执行。

## 现场发现与修复

1. **CSV错误刷新丢旧表**：真实测试先上传2行，再用重复表头刷新，接口返回错误但旧表已被DROP。
   复现仅使用随机验收文件，未影响原有资料。补了5个后端回归和1个前端行为回归，先全部失败，再修复到全部通过。
   现已校验UTF-8、列名与清洗碰撞、行宽及表归属；文件/SQL正常请求异常会回滚，只有成功文件进入saved。
2. **错误被显示成成功**：上传UI原来不检查每张表的error，错误也提示“已上传/建表”。
   现在给出具体失败原因；快速连续消息只保留最新一条，避免旧成功提示遮挡错误。已用真实浏览器上传、失败刷新、查询和删除复验。
3. **长SSE取证脚本问题**：首轮模型构建实际成功，但Chrome清理了Network域中的长响应体，脚本的`response.text()`失败。
   已保留完成页面截图与已落盘IR，修正为读取真实Response的克隆流；从已有图谱继续验收，没有重跑构建。
4. **UI验收退出码遗漏**：旧走查脚本会打印累计控制台错误，却可能返回0。
   重启期间的一次连接重置暴露该问题，已把累计错误纳入失败条件，随后在不再重启服务的稳态窗口重测。
